# Дизайн: страница «Статистика»

## Проблема

В навигации уже есть пункт «Статистика» (`/stats`, `app-header.tsx:28`), но роут не
зарегистрирован — переход улетает на `*404` → редирект на главную. Страницы,
компонентов, эндпоинтов под неё нет вообще. При этом в проекте уже накоплено
1070 операций за 9 месяцев (январь–сентябрь 2026, BYN/EUR/USD, база — BYN),
и пользователь хочет получать из них инсайты: рост/падение по категориям,
динамику по месяцам, план/факт там, где он сам задал бюджет.

Собрано на живом брейншторме (grilling-сессия) с пользователем — ниже
зафиксированы принятые решения, не гипотезы.

## Цель (v1)

1. Два графика на странице `/stats`:
   - **Категории за месяц** — расходы по категориям с индикатором отклонения:
     % от заданного бюджета категории (если он есть) либо % от среднего по
     всей доступной истории (если бюджета нет).
   - **Динамика по месяцам** — расходы и доходы двумя линиями за всю
     доступную историю операций.
2. Селектор месяца (prev/next, дефолт — текущий) для графика категорий.
3. Все суммы — в базовой валюте семьи (`amountInHouseholdBaseCurrencyMinor`),
   без переключения по валютам.
4. Библиотека графиков — `solid-chartjs` (обёртка над `chart.js` для
   SolidJS; ни то ни другое сейчас не установлено).
5. Десктоп-приоритет: мобильная адаптация — best effort, не блокирует релиз.
   Лаконичный визуальный стиль — один акцентный график на блок.

## Не входит в v1

- Ручное бюджетирование как отдельная фича/сущность — у категорий уже есть
  опциональный `monthlyBudgetMinor` (`apps/api/src/infrastructure/database/schema/categories.ts:27`),
  переиспользуем как есть, новых полей и UI для его массового заведения не
  добавляем.
- Разрез по счетам, контактам, товарным позициям чеков.
- Переключение/фильтр по конкретной валюте.
- Скользящее окно сравнения (сейчас вся история — 9 месяцев, берём её
  целиком; пересмотреть на скользящее окно, когда истории станет 1.5–2+ года).
- Ручной переключатель тёмной темы — сейчас в проекте только
  `prefers-color-scheme`, живого JS-тоггла нет, графики читают цвета
  токенов один раз при монтировании.

## Подход

**Graph 1 — категории.** Новый эндпоинт `GET /api/operations/category-stats?month=YYYY-MM`.
Переиспользует существующий `OperationRepository.listMonthlyCategoryExpenses`
для сумм текущего месяца и новый метод `listCategoryExpenseHistory` — сумма
и количество различных месяцев (`count(distinct strftime('%Y-%m', happened_on))`)
по операциям строго до начала выбранного месяца. Сервис делит и считает
`deltaPercent` = отклонение текущего месяца от среднего по истории.

На фронте: если у категории задан `monthlyBudgetMinor` — используем уже
существующий `getCategoryBudgetSummary()` (`entities/category/model/selectors.ts:12`)
вместо серверного `deltaPercent`, т.е. план/факт к бюджету имеет приоритет
над сравнением с историей (закрытое решение брейншторма). Цвет столбца —
`category.color`, то есть тот же цвет, что уже используется на карточках
категорий (идентичность цвета = категория, без отдельной палитры).

**Graph 2 — динамика.** Новый эндпоинт `GET /api/operations/monthly-trend`
без параметров — агрегирует все операции household по
`strftime('%Y-%m', happened_on)` с раздельными суммами expense/income в
одном SQL-запросе (`sum(case when type = ... )`, как уже делает
`getSignedTotalsByAccount`). Две линии на графике, цвета — существующие
токены `--color-danger` (расход) и `--color-success` (доход), уже
используемые для этой семантики в `operations-table.module.scss:25-31`.

**Селектор месяца** переиспользует чистые функции периода из
`entities/operation/model/period.ts` (`shiftOperationPeriod`, `startOfPeriod`,
`canMoveToNextOperationPeriod`, `formatLocalDateKey`), зафиксированные на
`mode: 'month'` — без дублирования логики, уже работающей на главной
странице (`operations-workspace.tsx`).

## Модель данных

Изменений схемы БД нет — только новые агрегирующие SQL-запросы поверх
существующей таблицы `operations` и существующего поля
`categories.monthly_budget_minor`.

Новые контракты (`packages/contracts/src/operation.ts`):

| Тип | Поля |
|---|---|
| `CategoryStatItem` | `categoryId`, `currentMinor`, `averageMinor: number \| null`, `deltaPercent: number \| null`, `monthsIncludedCount` |
| `CategoryStats` | `baseCurrency`, `month`, `items: CategoryStatItem[]` |
| `MonthlyTrendPoint` | `month`, `expenseMinor`, `incomeMinor` |
| `MonthlyTrend` | `baseCurrency`, `points: MonthlyTrendPoint[]` |

Вход `category-stats` переиспользует существующую `getMonthlyExpenseSummaryInputSchema`
(`{ month: 'YYYY-MM' }`) — форма идентична, дублировать незачем.
`monthly-trend` параметров не принимает.

## Индикатор значимого отклонения

Порог значимости — `±20%`. Показываем процент у всех категорий, но визуально
акцентируем (цвет/насыщенность) только те, где `|deltaPercent| >= 20`.

## Открытые вопросы для будущих итераций

- Полноценное бюджетирование с уведомлениями о превышении.
- Разрез по счетам/контактам как отдельные виджеты статистики.
- Аналитика по товарным позициям чеков (требует парсинга `receiptImports.resultJson`,
  не прямого SQL-джойна — `receiptOperationLinks` связывает операцию с
  группой позиций, не с конкретным товаром).
- Скользящее окно сравнения вместо «вся история» — когда истории станет
  заметно больше.
