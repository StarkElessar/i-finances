# План реализации импорта чека по фотографии

## Назначение документа

Этот документ фиксирует план реализации концепции: пользователь фотографирует
чек, приложение распознает продавца, дату, итоговую сумму и товарные строки, а
затем предлагает создать операции семейного бюджета.

Первый вертикальный срез — загрузка, очередь, worker API, статусы и ручная
проверка — уже можно реализовывать независимо. Полноценное качество
категоризации и сопоставления продавцов проверяем **после завершения импорта
всех контактов и категорий из desktop macOS iFinances4**, потому что до этого у
модели не будет полной базы пользовательских категорий и привычек.

История OCR-прототипа, фактические замеры и подробный broker protocol описаны в
[receipt-ocr-migration-context.md](./receipt-ocr-migration-context.md).

## Ключевое решение

Распознанный чек не должен сразу попадать в `operations`.

Операции уже влияют на баланс, аналитику и историю счета, поэтому для AI-импорта
нужна отдельная сущность черновика чека:

- фото чека;
- сырой ответ модели;
- распознанные реквизиты продавца;
- распознанные строки товаров;
- предложенные категории;
- статус обработки;
- связь с созданными операциями после подтверждения пользователем.

Настоящие операции создаются только после review на отдельной странице.

Вся нейросетевая обработка выполняется локальным .NET worker-ом на Apple Mac
Mini. `i-finances` не вызывает cloud model API. Поскольку у Mac Mini нет белого
IP, worker сам устанавливает исходящее HTTPS-соединение с broker на публичном
VPS и забирает задания через pull/long-poll protocol.

## Целевой пользовательский сценарий

1. Пользователь открывает отдельную страницу импорта чеков.
2. Загружает или фотографирует чек.
3. Приложение создает запись импорта со статусом `uploaded`.
4. В той же DB-транзакции создаётся processing job и outbox event.
5. Dispatcher публикует задание в VPS broker.
6. Локальный .NET worker на Mac Mini арендует job, скачивает фото и обрабатывает
   его локальными моделями.
7. Worker возвращает broker versioned JSON, а broker доставляет подписанный
   callback в `i-finances`.
8. Сервер проверяет полностью готовый JSON, включая выбранные worker-ом
   категории, переводит суммы в копейки и переводит импорт в `needs_review`.
9. Пользователь видит экран проверки:
   - продавец;
   - дата операции;
   - счет списания;
   - итоговая сумма;
   - товарные строки;
   - предложенные категории;
   - будущие операции, сгруппированные по категориям.
10. Пользователь исправляет ошибки и подтверждает импорт.
11. Сервер создаёт одну или несколько `expense`-операций и связывает их с чеком.

## Что извлекаем из чека

Минимальный JSON результата:

```ts
type ParsedReceipt = {
    merchant: {
        address: string | null;
        displayName: string | null;
        legalName: string | null;
        unp: string | null;
    };
    currency: 'BYN';
    happenedOn: string;
    items: ParsedReceiptItem[];
    totalAmountMinor: number;
};

type ParsedReceiptItem = {
    discountMinor: number;
    name: string;
    quantity: number | null;
    totalMinor: number;
    unitPriceMinor: number | null;
};
```

`happenedOn` хранится как `YYYY-MM-DD`. Время чека на первом этапе не нужно.

## Изменения модели данных

### Контакты

Добавить к контактам УНП продавца:

- `unp`, nullable;
- нормализация УНП только до цифр;
- уникальность внутри `householdId` для непустого УНП;
- поиск контакта по УНП должен иметь приоритет выше поиска по названию.

Дополнительно рассмотреть таблицу алиасов:

- `contactAliases`;
- `contactId`;
- `name`;
- `normalizedName`;
- `source`, например `manual`, `receipt-ai`, `import-ifinances4`.

Это нужно, потому что пользователь знает магазин как `Санта`, а в чеке может
быть другое юрлицо.

### Чеки

Добавить `receipt_imports`:

- `id`;
- `householdId`;
- `accountId`, nullable до выбора счета пользователем;
- `status`: `uploaded`, `queued`, `processing`, `needs_review`, `approved`,
  `rejected`, `failed`, `cancelled`;
- `imagePath` или ссылка на объектное хранилище;
- `acceptedProcessingJobId`, nullable до принятия результата;
- `rawModelOutput`;
- `rawOcrText`, nullable;
- `pipelineVersion`;
- `modelVersions`;
- `merchantNameSnapshot`;
- `merchantLegalNameSnapshot`;
- `merchantUnpSnapshot`;
- `happenedOn`;
- `currency`;
- `totalAmountMinor`;
- `confidence`;
- `createdByUserId`, `createdAt`, `updatedAt`, `version`.

Добавить `receipt_processing_jobs`:

- `id`;
- `receiptImportId`;
- `brokerJobId`, nullable до публикации;
- `status`: `pending_publish`, `queued`, `leased`, `processing`, `completed`,
  `retry_wait`, `failed`, `dead_letter`, `cancelled`;
- `attempt`;
- `requestedPipelineVersion`;
- `workerId`, nullable;
- `resultSha256`, nullable;
- `lastError`, nullable;
- `queuedAt`, `startedAt`, `completedAt`, nullable;
- `createdAt`, `updatedAt`, `version`.

Добавить transactional outbox для надёжной публикации job в broker. Создание
`receipt_imports`, `receipt_processing_jobs` и outbox event должно происходить
одной DB-транзакцией.

Добавить `receipt_items`:

- `id`;
- `receiptImportId`;
- `sourceOrder`;
- `name`;
- `quantity`;
- `unitPriceMinor`;
- `discountMinor`;
- `totalMinor`;
- `categoryId`, nullable;
- `confidence`.

Добавить связь созданных операций с чеком:

- либо `receipt_operation_links`;
- либо `sourceReceiptImportId` в `operations`.

Предпочтительнее отдельная таблица связи: один чек может породить несколько
операций, а позже может понадобиться пересобрать связи без изменения самой
операции.

## AI-пайплайн

### Основной путь

Нейросетевой pipeline выполняется локальным .NET worker-ом на Apple Mac Mini.
Модели также работают локально. `i-finances` взаимодействует только с VPS broker
через versioned job protocol и не знает внутренних model endpoints.

Поток:

1. `i-finances` сохраняет private image и создаёт receipt import, processing job
   и outbox event.
2. Dispatcher идемпотентно публикует job в broker.
3. Worker делает outbound long poll и арендует job по lease token.
4. Worker получает bytes изображения через авторизованный binary endpoint или
   short-lived signed URL.
5. Worker выполняет OCR, собирает JSON чека и категоризирует товары по
   переданному снимку категорий.
6. Worker отправляет `complete` с `processingJobId`, lease token, result hash,
   pipeline/model versions и versioned JSON.
7. Broker отправляет подписанный callback в `i-finances`.
8. `i-finances` валидирует signature, schema version и result через Zod,
   нормализует money, сохраняет draft и переводит импорт в `needs_review`.

Worker не получает прямой доступ к БД и не обновляет `operations`. Повторная
выдача и доставка допустимы, поэтому publish, complete и callback должны быть
идемпотентными. Для долгих задач обязательны lease TTL и heartbeat.

### Внутренний pipeline worker-а

Принята трёхэтапная последовательность:

1. vision OCR извлекает максимально точный сырой текст;
2. text model преобразует OCR в versioned receipt JSON;
3. отдельная модель распределяет товары по категориям.

Вместе с заданием Mac Mini получает снимок всех доступных категорий семьи:
`id`, название и ключевые слова. Worker возвращает полностью готовый JSON с
исходными товарными строками и выбранным `categoryId` для каждой строки.
`i-finances` повторно проверяет эти ID и после ручного подтверждения создаёт
операции, сгруппированные по категориям.

## Server-side matching

LLM не принимает окончательных решений о создании контактов и операций.

Алгоритм продавца:

1. Если есть УНП, искать активный или архивный контакт по `householdId + unp`.
2. Если найден один контакт, использовать его.
3. Если УНП не найден, искать по `legalName`, `name` и алиасам.
4. Если есть уверенное совпадение, предложить его.
5. Если совпадения нет, создать черновое предложение нового контакта.
6. Новый контакт создается только при подтверждении пользователем.

Алгоритм категорий:

1. Сначала применять ключевые слова категорий.
2. Затем использовать историю уже подтвержденных receipt items.
3. Передать весь получившийся снимок категорий на Mac Mini.
4. Попросить локальную модель выбрать категорию только из этого списка.
5. Если уверенность низкая, оставить строку без категории и подсветить в review.

## Валидация

Импорт считается готовым к review, если:

- распознана дата;
- распознан итог;
- валюта поддерживается;
- есть хотя бы одна товарная строка;
- сумма строк с учетом скидок сходится с итогом или отличается в пределах
  допустимой копеечной погрешности;
- продавец найден или предложен новый контакт;
- каждая строка имеет `confidence`.

Если сумма не сходится:

- статус `needs_review`;
- UI показывает расхождение;
- автосоздание операций запрещено.

## Отдельная страница

Маршрут:

- `src/routes/(app)/receipts.tsx`;
- `src/views/receipts/page.tsx`.

Основные зоны страницы:

- загрузка фото;
- список последних импортов;
- preview чека;
- таблица товарных строк;
- блок продавца;
- выбор счета;
- группировка будущих операций по категориям;
- кнопки `Подтвердить`, `Отклонить`, `Повторить распознавание`.

Для первой версии страница может быть доступна из основной навигации как
`Чеки`.

## Метрики готовности MVP

- 90%+ чеков корректно распознают дату и итоговую сумму.
- 90%+ чеков корректно связываются с контактом при наличии УНП.
- 80%+ товарных строк имеют корректную сумму после скидок.
- 70%+ товарных строк получают приемлемую категорию без ручной правки.
- Ни одна job не теряется между DB и broker.
- Повторный callback не создаёт дубликаты и не перезаписывает approved import.
- Ни одна операция не создается без подтверждения пользователя.
- Ошибочный чек не ломает баланс и не попадает в ledger автоматически.

## Открытые вопросы

- Использовать callback broker → `i-finances` или дополнительный result polling.
- Какой lease TTL, heartbeat interval и максимальное число attempts.
- Через сколько дней после создания операций удалять фото.
- Нужен ли автоматический поиск банковской операции по сумме и дате для выбора
  счета.
- Как показывать несколько похожих контактов, если УНП не распознан.

Принятые ответы:

- фото хранится в `static/receipts` на отдельном production-томе;
- в БД хранится внутренний адрес, защищённый endpoint отдаёт байты;
- категоризацию выполняет Mac Mini по снимку всех доступных категорий;
- worker возвращает полностью готовый JSON;
- сырой OCR-текст хранится вместе с результатом до удаления данных чека;
- авторизация worker API выполняется отдельным API-ключом поверх HTTPS.
