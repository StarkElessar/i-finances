# Ротация текущего сеанса при смене пароля

Задача IF-46. Автор: Sonnet по заданию Opus, 2026-10-18. Статус: реализовано, ждёт ревью. Смена пароля (IF-41) описана в `telegram-auth-and-households-v1.md` и в коде `SecurityService.changePassword`.

## Было

Смена пароля завершала все **другие** сеансы пользователя, а текущий оставался с прежним токеном. Если cookie текущего сеанса украдена (XSS в расширении, чужой компьютер, лог прокси), то после смены пароля вор остаётся в аккаунте: ради этого пароль, как правило, и меняют.

## Решение

В той же транзакции, где сохраняется новый хеш пароля и удаляются остальные сеансы, у текущего сеанса заменяется `token_hash` на хеш нового случайного токена (`PasswordUserRepository.replacePasswordAndRevokeOtherSessions`, поле `rotatedTokenHash`).

- Токен создаётся тем же генератором, что при входе (`generateSessionToken()`: 32 байта CSPRNG, base64url; `SessionService` берёт его по умолчанию, `SecurityService` тоже). В базе лежит только SHA-256 хеш.
- Строка сеанса остаётся той же: `id`, `createdAt`, `expiresAt`, `lastSeenAt`, `ipAddress`, `userAgent` не меняются. Меняется только секрет.
- Старый токен перестаёт работать в момент коммита транзакции (поиск идёт по `token_hash`), отдельного списка отозванных токенов не нужно.
- Контроллер (`SecurityHttpController.changePassword`) получает от сервиса `rotatedSession { token, expiresAt }` и отдаёт `Set-Cookie` через `createSessionCookie`, то есть с теми же атрибутами, что при входе: `Path=/`, `HttpOnly`, `SameSite=Lax`, `Secure` в production, `Expires`.
- **Срок жизни не продлевается**: `Expires` cookie равен `expires_at` сеанса из базы. Смена пароля не новый вход, и срок сеанса остаётся прежним; cookie и строка в базе не расходятся.
- Тело ответа не изменилось: `{ ok, revokedSessionCount }`. `revokedSessionCount` по-прежнему считает только другие сеансы.
- Cookie выставляется только при успешной смене. Отказы (неверный пароль, тот же пароль, плохой ввод, лимит) ничего не ротируют и `Set-Cookie` не отдают.
- Если текущий сеанс исчез между проверкой сессии и транзакцией (параллельный выход), пароль всё равно меняется, остальные сеансы завершаются, ротации нет и cookie не выставляется (`rotatedSession` пуст).
- Ротация относится только к смене пароля. Вход, выход, passkey и остальные маршруты раздела «Безопасность» не менялись.

## Что видит интерфейс

- Браузер заменяет cookie сам, пользователь ничего не замечает: вкладка остаётся открытой, следующие запросы уходят с новым токеном.
- В списке сеансов запись текущего устройства та же: прежний `id`, `isCurrent: true`, прежние даты и метаданные.
- Другие устройства и вор с украденной cookie получают `401` и выходят.
- Запрос, который был в полёте со старой cookie в момент смены, получит `401`. Для одного пользователя с одним активным окном это приемлемо.
- Клиент API, который хранит cookie вручную (не браузер), должен принять `Set-Cookie` из ответа. MCP-ключ раздел «Безопасность» не использует (только cookie-резолвер).

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Удалять и текущий сеанс, требовать повторного входа | Пользователь только что ввёл пароль; принудительный выход раздражает и ничего не добавляет, раз новый секрет можно выдать сразу. |
| Создать новую строку сеанса вместо замены токена | Меняется `id` сеанса и пропадают `createdAt` и метаданные: список «Устройства» показывал бы новый вход, а клиент, держащий `id` текущего сеанса, ломался бы. |
| Ротировать токен отдельным запросом после смены пароля | Окно между двумя запросами, в котором вор всё ещё в системе, и риск, что вторая часть не выполнится. Одна транзакция атомарна. |
| Продлевать срок на новые 30 дней | Продление не нужно для безопасности и меняет смысл `expires_at`; сеанс не получает привилегий, которых у него не было. Можно добавить позже, если решим продлевать сеанс при любом повторном вводе пароля. |
| Список отозванных токенов (denylist) | Новая таблица (миграции запрещены) и лишнее состояние, когда достаточно заменить хеш в существующей строке. |
