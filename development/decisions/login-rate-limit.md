# Лимит входа по паролю

Задача IF-45, пункты 2 и 3. Автор: Sonnet по заданию Opus, 2026-10-18. Статус: реализовано, ждёт ревью. Адрес клиента для ключей лимита определяется по `client-ip.md`.

## Что было

`LoginRateLimiter` считал неудачи по ключу `ip:username` (5 за 15 минут). Адрес приходил из первого элемента `X-Forwarded-For`, то есть от клиента, поэтому смена заголовка в каждом запросе давала неограниченный перебор. Даже с исправленным адресом ключ по паре не защищает от источника, у которого много адресов (ботнет, подсеть IPv6 /64).

## Решение: три независимых счётчика

| Счётчик | Ключ | Порог (по умолчанию) | Окно |
|---|---|---|---|
| Пара | `ip:username` | 5 неудач | 15 минут |
| Логин | `username` | 20 неудач с любых адресов | 15 минут |
| Адрес | только IP | 30 неудач на любые логины | 15 минут |

Вход блокируется, если превышен **любой** из трёх. Ответ при блокировке прежний: `429 rate-limited`; заголовка `Retry-After` в ответе нет (так было и раньше). Лимитер считает `retryAfterSeconds` как большее из двух ожиданий, но API его пока не отдаёт.

**Тип блокировки по логину: временная, фиксированное окно.** Окно начинается с первой неудачи и не продлевается следующими, блокировка заканчивается сама не позже чем через 15 минут после первой неудачи окна. Постоянной блокировки нет: чужой не может заблокировать владельца навсегда. Пока он перебирает чужой логин, владелец с паролем теряет доступ не дольше окна; затем счётчик обнуляется. Принятая цена: настойчивый злоумышленник может удерживать блокировку, повторяя 20 запросов в 15 минут. Смягчение: вход по ключу доступа (passkey) лимитером не затрагивается, ключ работает и во время блокировки пароля.

Порог 20 выбран так, чтобы несколько опечаток владельца с разных устройств (5 на пару) не блокировали вход, а перебор оставался в пределах 20 попыток на окно, то есть около 1900 в сутки на логин (для пароля от 12 символов, `min(12)` в контракте, это пренебрежимо).

Успешный вход обнуляет только счётчик пары. Счётчик логина не сбрасывается: иначе обычный вход владельца давал бы подбирающему новый запас.

Несуществующие логины считаются точно так же (иначе лимит выдавал бы, есть ли учётная запись).

## Атомарность: попытка резервируется до проверки пароля

Было: `check` → `await verify` (десятки миллисекунд Argon2) → `recordFailure`. N параллельных запросов все проходили `check` до первой записи неудачи, лимит не работал против одновременных попыток.

Стало: `tryReserve` проверяет оба порога и **тут же** увеличивает оба счётчика в одном синхронном шаге (между проверкой и записью нет `await`, JS однопоточен), и только потом сервис идёт в базу и в `verify`. Параллельные запросы получают не больше `maxAttempts` проверок на пару. Если вход удался, `recordSuccess` удаляет счётчик пары и возвращает одну попытку счётчику логина.

Следствия, принятые сознательно:

- Если `findByUsername` или `verify` бросят исключение (500), попытка остаётся посчитанной: безопаснее, чем отдавать её обратно.
- Заблокированный запрос сам счётчик не увеличивает, поэтому блокировка заканчивается вместе с окном первой попытки, а не продлевается потоком запросов.
- Возврат попытки при успехе не привязан к окну: если окно истекло между резервированием и успехом, будет вычтена единица из нового окна. Погрешность в одну попытку, в безопасную для владельца сторону.

## Лимит по одному адресу (password spraying)

Пара и логин не останавливают источник, который перебирает **много разных логинов** с одного адреса, пробуя один популярный пароль: на каждую пару приходится по одной попытке. Третий счётчик ключуется **только по адресу** (30 неудач за 15 минут на любые логины, настраивается `maxAttemptsPerIp`). `tryReserve` оценивает его вместе с остальными, и сработать может любой.

- Заблокированная попытка счётчик не увеличивает. Успешный вход возвращает одну попытку (`recordSuccess`), поэтому общий адрес за NAT не «съедается» нормальными входами.
- Если адрес неизвестен (`ipAddress` не передан), счётчик не применяется: иначе все такие запросы слились бы в один общий ключ и заблокировали бы всех.
- **Вход по ключу доступа лимитером не затрагивается** (passkey не проходит через `LoginRateLimiter`).
- **Лимитер смены пароля (IF-41)** ключуется `unknown:<userId>` без адреса и должен оставаться простым счётчиком на пользователя, поэтому в `composition-root.ts` он создаётся с `maxAttemptsPerIp` и `maxAttemptsPerUsername` равными `Infinity`. Без адреса адресный счётчик к нему и так не применяется; бесконечность делает это явным.
- Побочный эффект, о котором нужно знать до настройки `TRUSTED_PROXY_COUNT=1`: см. «Допущения» в `client-ip.md`. Пока адрес клиента равен адресу nginx, этот счётчик общий для всех клиентов.

## Аккаунты без пригодного пароля и время ответа

`verify` из `@node-rs/argon2` бросает исключение на значении, которое не является Argon2 PHC-строкой (проверено: «password hash string missing field»), и вход давал 500 вместо 401. Теперь:

- `hasUsablePassword(hash)` (`modules/auth/has-usable-password.ts`, принимает `string | null | undefined`, чтобы пережить DB-2 из IF-44) пропускает только `$argon2id$`, `$argon2i$`, `$argon2d$`. Если IF-41 вводит такую же функцию, при слиянии оставить одну.
- Для неизвестного логина, неактивного пользователя и аккаунта без пригодного хеша выполняется «холостая» проверка над заранее посчитанным валидным хешем `DUMMY_PASSWORD_HASH` (те же параметры стоимости, что у `PasswordService`; тест следит, что строка читается настоящим проверяющим и параметры совпадают). Время ответа не отличается от неверного пароля, статус и текст те же (`401 invalid-credentials`). Результат холостой проверки никогда не даёт входа.
- Исключение проверяющего (повреждённый хеш) трактуется как неверный пароль и пишется в лог без хеша.

Холостая проверка для неизвестных и неактивных пользователей добавлена сверх пункта задачи: без неё время ответа выдавало существование логина. Статусы и тела ответов не менялись.

## Память

Счётчики в оперативной памяти (после перезапуска сбрасываются; как и раньше, один процесс API). Общий класс `FixedWindowCounter` (один файл) периодически вычищает истёкшие ключи, поэтому поток случайных логинов не растёт без границ (раньше записи удалялись только при повторном обращении к тому же ключу). Его же берут новые лимиты IF-44 (A1).

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Только исправить адрес клиента | Остаются ботнет и IPv6 /64. |
| Постоянная блокировка после N неудач | Чужой навсегда запирает владельца. |
| Растущая задержка (экспоненциальный backoff) на логин | Нужно хранить состояние на логин дольше окна и объяснять владельцу; для одного пользователя выигрыш невелик. |
| Сбрасывать счётчик логина при успешном входе | Подбирающий получает новый запас каждый раз, когда владелец входит. |
| Хранить счётчики в SQLite | Миграции запрещены в задаче, а один процесс API не требует общего хранилища. |
