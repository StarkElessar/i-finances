# Лимит входа по паролю

Задача IF-45, пункты 2 и 3. Автор: Sonnet по заданию Opus, 2026-10-18. Статус: принято (ревью Opus пройдено). Адрес клиента для ключей лимита определяется по `client-ip.md`.

## Что было

`LoginRateLimiter` считал неудачи по ключу `ip:username` (5 за 15 минут). Адрес приходил из первого элемента `X-Forwarded-For`, то есть от клиента, поэтому смена заголовка в каждом запросе давала неограниченный перебор. Даже с исправленным адресом ключ по паре не защищает от источника, у которого много адресов (ботнет, подсеть IPv6 /64).

## Решение: три независимых счётчика

| Счётчик | Ключ | Порог (по умолчанию) | Окно |
|---|---|---|---|
| Пара | `ip:username` | 5 неудач | 15 минут |
| Логин | `username` | 20 неудач с любых адресов | 15 минут |
| Адрес | IPv4 целиком, IPv6 по префиксу /64 | 30 неудач на любые логины | 15 минут |

Вход блокируется, если превышен **любой** из трёх. Ответ при блокировке прежний: `429 rate-limited`; в ответ добавляется заголовок `Retry-After` (секунды до конца самого долгого из сработавших окон; в тело ответа это значение не попадает). Для смены пароля (IF-41) заголовок пока не добавлен.

**Тип блокировки по логину: временная, фиксированное окно.** Окно начинается с первой неудачи и не продлевается следующими, блокировка заканчивается сама не позже чем через 15 минут после первой неудачи окна. Постоянной блокировки нет: чужой не может заблокировать владельца навсегда. Пока он перебирает чужой логин, владелец с паролем теряет доступ не дольше окна; затем счётчик обнуляется. Принятая цена: чужой может запереть вход по паролю чужому логину. Пока `TRUSTED_PROXY_COUNT=1` и адреса настоящие, пара ограничивает один адрес пятью попытками, поэтому до порога 20 нужны запросы **как минимум с четырёх разных адресов** (5+5+5+5); это могут быть адреса одного IPv6 /64, но вся сеть теперь делит адресный бюджет 30. Блокировка повторяется каждое окно, пока атака идёт. Пока `TRUSTED_PROXY_COUNT` не задан, всё хуже, см. `client-ip.md`. Вход по ключу доступа (passkey) и через Telegram лимитерами пароля не затрагивается.

Порог 20 выбран так, чтобы несколько опечаток владельца с разных устройств (5 на пару) не блокировали вход, а перебор оставался в пределах 20 попыток на окно, то есть около 1900 в сутки на логин (для пароля от 12 символов, `min(12)` в контракте, это пренебрежимо).

Успешный вход удаляет счётчик пары и возвращает по одной попытке счётчикам логина и адреса. Счётчики логина и адреса не обнуляются: иначе обычный вход владельца давал бы подбирающему новый запас. Цена возврата: держатель действующего аккаунта получает одну лишнюю попытку перебора на каждый свой успешный вход; при двух пользователях это приемлемо.

Несуществующие логины считаются точно так же (иначе лимит выдавал бы, есть ли учётная запись).

## Атомарность: попытка резервируется до проверки пароля

Было: `check` → `await verify` (десятки миллисекунд Argon2) → `recordFailure`. N параллельных запросов все проходили `check` до первой записи неудачи, лимит не работал против одновременных попыток.

Стало: `tryReserve` проверяет все три порога и **тут же** увеличивает все три счётчика в одном синхронном шаге (между проверкой и записью нет `await`, JS однопоточен), и только потом сервис идёт в базу и в `verify`. Параллельные запросы получают не больше `maxAttempts` проверок на пару. Если вход удался, `recordSuccess` удаляет счётчик пары и возвращает по одной попытке счётчикам логина и адреса.

Следствия, принятые сознательно:

- Если `findByUsername` или `verify` бросят исключение (500), попытка остаётся посчитанной: безопаснее, чем отдавать её обратно.
- Заблокированный запрос сам счётчик не увеличивает, поэтому блокировка заканчивается вместе с окном первой попытки, а не продлевается потоком запросов.
- Возврат попытки при успехе не привязан к окну: если окно истекло между резервированием и успехом, будет вычтена единица из нового окна. Погрешность в одну попытку, в безопасную для владельца сторону.

## Лимит по одному адресу (password spraying)

Пара и логин не останавливают источник, который перебирает **много разных логинов** с одного адреса, пробуя один популярный пароль: на каждую пару приходится по одной попытке. Третий счётчик ключуется **по IPv4-адресу или IPv6-префиксу /64** (30 неудач за 15 минут на любые логины, настраивается `maxAttemptsPerIp`). `tryReserve` оценивает его вместе с остальными, и сработать может любой. `loginAddressKey` работает с уже проверенным `http/client-ip` адресом: разворачивает сжатие IPv6, нормализует hextet-слова первых 64 бит и отбрасывает идентификатор интерфейса. Разные записи одной сети получают один ключ. Порядок трёх проверок, ключ пары с полным IP, метаданные сеанса и публичные ответы не меняются; возврат попытки при успехе использует тот же /64-ключ.

- Заблокированная попытка счётчик не увеличивает. Успешный вход возвращает одну попытку (`recordSuccess`), поэтому общий адрес за NAT не «съедается» нормальными входами.
- Если адрес неизвестен (`ipAddress` не передан), счётчик не применяется: иначе все такие запросы слились бы в один общий ключ и заблокировали бы всех.
- **Вход по ключу доступа лимитером не затрагивается** (passkey не проходит через `LoginRateLimiter`).
- **Лимитер смены пароля (IF-41)** ключуется `unknown:<userId>` без адреса и должен оставаться простым счётчиком на пользователя, поэтому в `composition-root.ts` он создаётся с `maxAttemptsPerIp` и `maxAttemptsPerUsername` равными `Infinity`. Без адреса адресный счётчик к нему и так не применяется; бесконечность делает это явным.
- Побочный эффект, о котором нужно знать до настройки `TRUSTED_PROXY_COUNT=1`: см. «Допущения» в `client-ip.md`. Пока адрес клиента равен адресу nginx, этот счётчик общий для всех клиентов.

## Порог по адресу и обязательный TRUSTED_PROXY_COUNT

Решение ревьюера (Opus, повторное ревью IF-45, 2026-10-18).

**Порог 30 неудач за 15 минут оставляем.** Обоснование:

- Пользователей двое. Чтобы владелец запер сам себя из дома (общий NAT семьи), нужно 30 неудачных входов за 15 минут с одного адреса на любые логины; при пяти на пару это шесть «исчерпанных» пар подряд. Обычные опечатки до этого не доходят, успешный вход возвращает попытку.
- Общий NAT с посторонними (CGNAT мобильного оператора, публичный Wi-Fi) упирается в порог, только если кто-то за тем же адресом целенаправленно перебирает пароли этого сервиса. Тогда блокировка адреса и есть нужное поведение; ключ доступа продолжает работать.
- Против перебора одного пароля по логинам 30 за окно это около 2900 попыток в сутки с адреса, что для паролей от 12 символов пренебрежимо. Ниже порог не дал бы заметной защиты, но приблизил бы самоблокировку за NAT; выше ослабил бы защиту без выигрыша для двух пользователей.
- Источник с подсетью IPv6 /64 меняет ключ пары, но вся подсеть делит адресный счётчик (30); для одного логина также действует порог 20.

**Безопасный дефолт 0 оставляем для разработки и тестов, но в production значение обязательно.** Варианты:

| Вариант | Решение | Почему |
|---|---|---|
| Оставить молчаливый дефолт 0 везде | нет | За nginx все клиенты = адрес nginx: любой запирает вход по паролю владельца пятью запросами, 30 чужих неудач запирают всех. Ошибка конфигурации ничем не видна. |
| Дефолт 1 | нет | При прямом доступе к API (разработка, ошибка в сети docker) правый элемент `X-Forwarded-For` подделывает клиент, см. `client-ip.md`. |
| Предупреждение в логе при старте | нет | Лог на сервере никто не читает при выкатке; деградация останется незамеченной до атаки. |
| Предупреждение на запрос, если пришёл `X-Forwarded-For` при значении 0 | нет | Шум в логе на каждый запрос и та же проблема: никто не смотрит. |
| **Отказ запуска при `NODE_ENV=production` без явного `TRUSTED_PROXY_COUNT`** | **да** | Ошибка видна сразу на шаге выкатки (контейнер не станет `healthy`), исправление в одну строку env. Явный `0` разрешён: API, к которому клиенты подключаются напрямую, остаётся возможным, но это осознанное решение, а не забытая переменная. Пустая строка считается «не задано» (иначе `z.coerce` превратил бы её в 0). |

Реализация: `assertTrustedProxyCountIsExplicit` в `modules/auth/auth-config.ts`, вызывается из `getAuthConfig()` (первый вызов в `createApiDependencies`, то есть при старте `main.ts` и `cleanup-receipt-images.ts`). `NODE_ENV=production` задан в `apps/api/Dockerfile`. Тесты: `tests/auth-config.test.ts`.

## Аккаунты без пригодного пароля и время ответа

`verify` из `@node-rs/argon2` бросает исключение на значении, которое не является Argon2 PHC-строкой (проверено: «password hash string missing field»), и вход давал 500 вместо 401. Теперь:

- `hasUsablePassword(hash)` (`modules/auth/has-usable-password.ts`, принимает `string | null | undefined`, чтобы пережить DB-2 из IF-44) пропускает только полную PHC-строку Argon2 (вариант `argon2id`/`argon2i`/`argon2d`, версия, параметры стоимости, соль и хеш); префикса `$argon2id$` недостаточно. Если IF-41 вводит такую же функцию, при слиянии оставить одну.
- Для неизвестного логина, неактивного пользователя и аккаунта без пригодного хеша выполняется «холостая» проверка над заранее посчитанным валидным хешем `DUMMY_PASSWORD_HASH` (те же параметры стоимости, что у `PasswordService`; тест следит, что строка читается настоящим проверяющим и параметры совпадают). Время ответа не отличается от неверного пароля, статус и текст те же (`401 invalid-credentials`). Результат холостой проверки никогда не даёт входа.
- Исключение проверяющего (повреждённый хеш) трактуется как неверный пароль и пишется в лог без хеша.

Холостая проверка для неизвестных и неактивных пользователей добавлена сверх пункта задачи: без неё время ответа выдавало существование логина. Статусы и тела ответов не менялись.

## Память

Счётчики в оперативной памяти (после перезапуска сбрасываются; один процесс API). Прежняя периодическая очистка не ограничивала память внутри 15-минутного окна: каждый новый IP и логин добавлял ключи. Теперь у каждого `FixedWindowCounter` жёсткий предел **10 000 ключей** по умолчанию. Три счётчика входа вместе занимают не больше **30 000 записей**; `LoginRateLimiter.size` показывает их общее количество. `LOGIN_RATE_LIMIT_MAX_KEYS` задаёт предел каждого счётчика публичного входа; прочие пользователи общего `FixedWindowCounter` (смена пароля, Telegram, приглашения) получают тот же конечный дефолт 10 000.

При добавлении сначала удаляются истёкшие окна (старые истёкшие записи не могут вытеснить активные). Если место ещё занято, вытесняется запись с самым старым началом окна, затем новый ключ принимается. Повторный increment активного ключа не меняет его возраст и не вытесняет соседей. Заполненность сама по себе не возвращает 429 и не блокирует всех новых пользователей. Очистка запускается не раньше ближайшего известного истечения; при заполнении полностью активными ключами нет полного обхода Map на каждое добавление.

**Принятый компромисс:** поток разных активных ключей может вытеснить ещё действующий бюджет пары, адреса или логина и тем самым ослабить защиту от перебора. Сохраняем конечную память и возможность новых входов, а общий допуск ниже удерживает загрузку Argon2 независимо от числа ключей. При нескольких процессах лимиты отдельные в каждом; распределённого состояния здесь нет.

## Общий допуск к проверке пароля (решение владельца, 2026-10-23)

Три счётчика не ограничивают общий CPU: 5000 запросов с разными IP и логинами проходили все три порога и запускали Argon2 одновременно, включая холостые проверки неизвестных пользователей. `PasswordVerificationLimiter` — отдельный класс в `password-verification-limiter.ts`, один экземпляр на процесс в composition root рядом с `LoginRateLimiter`. Он допускает **8** выполняющихся входов, хранит **64** ожидающих в FIFO и отказывает остальным сразу. Максимум ожидания — **2000 мс**; по истечении запрос удаляется из очереди и тоже получает отказ. Освобождение слота передаёт его старейшему ещё живому запросу. Часы, постановка и отмена таймеров внедряемые; истечение проверяется также при передаче слота, если event loop задержал callback таймера.

Порядок: прежние Origin и предел тела → разбор контракта → общий допуск → прежний атомарный `tryReserve` трёх счётчиков → поиск пользователя → настоящая или холостая проверка → прежняя транзакционная проверка хеша при записи сеанса. Ожидающий запрос ещё не читает счётчики и не создаёт ключи. Общий допуск возвращает прежний **429 `{ ok: false, errorCode: 'rate-limited', message }`**, `Retry-After: 2` (округлённое вверх время ожидания в секундах); полей `reason` в контракте входа нет, контракт не менялся. И переполнение, и тайм-аут **не являются неудачной попыткой**, не вызывают `tryReserve` / `recordSuccess` и не меняют бюджет. У обычного отказа трёх счётчиков остаётся прежний `Retry-After` до конца окна.

Слот удерживается от допуска до завершения входа и освобождается в `finally` при любом результате, включая исключение репозитория. Тайм-аут относится только к очереди: уже выполняющийся Argon2 не отменяется и не отдаёт слот раньше завершения. Граница защищает публичный вход по паролю; смена пароля использует свой прежний лимитер. Passkey и Telegram не получают эту зависимость и продолжают работать при заполненной очереди пароля.

Конфигурация проверяется `getPasswordSignInConfig` при сборке приложения; неверные значения останавливают запуск. Примеры: `apps/api/.env.example` и корневой `.env.example`. Команды API читают **корневой `.env`**, файл внутри `apps/api` служит справкой.

| Переменная окружения | Дефолт | Допустимые значения |
|---|---:|---|
| `PASSWORD_VERIFY_MAX_CONCURRENT` | 8 | целое 1–8 |
| `PASSWORD_VERIFY_MAX_QUEUE` | 64 | целое 0–64; 0 отключает очередь |
| `PASSWORD_VERIFY_QUEUE_TIMEOUT_MS` | 2000 | целое 1–10000, миллисекунды |
| `LOGIN_RATE_LIMIT_MAX_KEYS` | 10000 | целое 1–100000, на каждый из трёх счётчиков |

Переменные можно опустить для дефолтов. При уменьшении тайм-аута `Retry-After` остаётся не меньше одной секунды.

Тесты: `auth.test.ts` — залп 200 разных IP/логинов, максимум 8 вызовов проверяющего одновременно, 64 ожидающих, 128 немедленных 429 с заголовком, 0 ключей и попыток у отказанных/ожидающих, продолжение очереди и полный бюджет отвергнутого источника, отдельный HTTP-тайм-аут. `password-verification-limiter.test.ts` — FIFO, освобождение мест после тайм-аута, отложенный callback, отмена таймеров, повторный release, очередь 0. `password-sign-in-service.test.ts` — освобождение слота после исключений и прежняя защита от гонки смены пароля. `login-rate-limiter.test.ts` — /64, возврат попытки, сжатые/полные IPv6, предел каждого счётчика и вытеснение активных/истёкших записей. `password-sign-in-config.test.ts` — дефолты и отклонение неверного env.

## Размер тела запроса входа (ревью Codex, 2026-10-23)

`POST /api/auth/sign-in` раньше разбирал JSON целиком до проверки `Origin` и до лимитера, без верхнего предела: тело в 64 КБ принималось, а бесконечный поток без `Content-Length` читался десятки секунд. Теперь маршрут явно собирается в порядке `signInOriginGuard → signInBodyLimit → signIn`: отдельный middleware (`http/mutation-origin-guard.ts`) проверяет `Origin` **до** `bodyLimit` на 16 КиБ (самое большое корректное тело — логин 64 символа, пароль 256, `returnTo` 2048, до 4 байт на символ — меньше 12 КиБ). Это существенно для Hono: без `Content-Length` `bodyLimit` сам читает поток до вызова `next()`, поэтому проверки только в обработчике недостаточно. Чужой `Origin` получает `403 invalid-origin` без чтения тела, в том числе для бесконечного chunked-потока. Для допустимого `Origin` с `Content-Length` больше предела ответ `413 payload-too-large` без чтения; без `Content-Length` чтение прекращается на первой порции, превысившей предел. Код `payload-too-large` добавлен в `passwordSignInErrorCodes` (аддитивно).

Тот же порядок применяется к `POST /api/auth/passkey/sign-in/options` и `/verification`: 16 КиБ, ответ `413 payload-too-large`. Вход по ключу доступа по-прежнему не использует `LoginRateLimiter`. `POST /api/auth/passkey/registration/verification` требует cookie-сеанс; его тело ограничено 64 КиБ, чтобы вместить attestation с цепочкой сертификатов, с проверкой `Origin` перед лимитом и проверкой сеанса после него. `payload-too-large` добавлен в оба контракта ошибок passkey. Тесты считают прочитанные порции потока (без prefetch), проверяют отсутствие чтения при чужом `Origin`, превышение на один байт и допустимое тело ровно на границе с `Content-Length` и chunked.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Только исправить адрес клиента | Остаются ботнет и IPv6 /64. |
| Постоянная блокировка после N неудач | Чужой навсегда запирает владельца. |
| Растущая задержка (экспоненциальный backoff) на логин | Нужно хранить состояние на логин дольше окна и объяснять владельцу; для одного пользователя выигрыш невелик. |
| Сбрасывать счётчик логина при успешном входе | Подбирающий получает новый запас каждый раз, когда владелец входит. |
| Хранить счётчики в SQLite | Миграции запрещены в задаче, а один процесс API не требует общего хранилища. |
