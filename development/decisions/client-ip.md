# IP клиента за обратным прокси

Задача IF-45, пункт 1 (находка Р11 из `telegram-auth-and-households-v1.md`, задача A1). Автор: Sonnet по заданию Opus, 2026-10-18. Статус: реализовано, ждёт ревью.

## Проблема

`createMetadata` в `auth-controller.ts` и `passkey-controller.ts` брал **первый** элемент `X-Forwarded-For`. Nginx в homelab выставляет `X-Forwarded-For $proxy_add_x_forwarded_for`, то есть **дописывает** адрес соседа в конец уже пришедшего заголовка. Всё левее последнего элемента присылает сам клиент. Следствия:

- ключ лимитера входа по паролю (`ip:username`) менялся одним заголовком, перебор пароля был неограниченным;
- в `sessions.ip_address` попадал адрес, придуманный клиентом (подделка журнала входов).

## Что известно о цепочке прокси (проверено по файлам)

Источник: `/Users/stark/Documents/web/homelab/nginx/conf.d/default.conf`, `docker-compose.yml`, `README.md` homelab.

```text
Клиент ──TLS──► nginx (контейнер homelab_nginx, порты 80/443 наружу) ──HTTP──► i_finances_api:3001 (сеть if-net)
```

- Ровно **один** прокси, которым мы владеем: nginx. Он терминирует TLS (Let's Encrypt), CDN или другого балансировщика в конфигурации нет.
- У `if-api` нет секции `ports`: порт 3001 снаружи недоступен, достучаться до API можно только через nginx внутри docker-сети `if-net`.
- Для `location /api/` nginx ставит `X-Real-IP $remote_addr` и `X-Forwarded-For $proxy_add_x_forwarded_for`.

**Не проверено (допущения):** что перед VPS не стоит внешний прокси или CDN (в DNS/фаерволе); что реальный `env/i-finances.env` на сервере не содержит лишнего (в репозитории только `.example`); поведение IPv6-клиентов через docker-proxy. См. «Допущения».

## Решение

Один модуль `apps/api/src/http/client-ip.ts`:

- `resolveClientIp({ forwardedFor, socketAddress, trustedProxyCount })` — чистая функция;
- `readClientIp(context, trustedProxyCount)` — обёртка для контроллеров (адрес TCP-соседа берётся через `getConnInfo` из `@hono/node-server/conninfo`).

Правила:

1. Настройка `TRUSTED_PROXY_COUNT` (env, целое 0–10, **по умолчанию 0**), читается в `getAuthConfig()` как `AuthConfig.trustedProxyCount`.
2. `0` — заголовки не доверяются вообще, адрес клиента = адрес TCP-соседа.
3. `N > 0` — клиент это N-й элемент `X-Forwarded-For` **справа**. Каждый наш прокси дописывает адрес своего соседа, поэтому правый край написан нашей инфраструктурой, а всё левее — клиентом. Для нашей схемы (один nginx) нужно `TRUSTED_PROXY_COUNT=1`: берётся ровно тот адрес, который nginx дописал из `$remote_addr`.
4. Если заголовка нет, он короче цепочки, или нужный элемент не является IP-адресом — возвращается адрес TCP-соседа (его клиент подделать не может), а не предположение из заголовка.
5. Адрес нормализуется: нижний регистр, `::ffff:1.2.3.4` превращается в `1.2.3.4`. Невалидные строки отбрасываются (`net.isIP`), так что длинный мусор в `ipAddress` попасть не может.
6. При записи сеанса (`SessionService.createSession`, общий путь пароля и ключей доступа) `ipAddress` обрезается до 64 символов, `userAgent` до 512.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Первый элемент `X-Forwarded-For` (как было) | Его присылает клиент. |
| Только `X-Real-IP` | Работает за нашим nginx (он перезаписывает заголовок), но привязывает код к конкретному прокси; при отсутствии или подделке (прямой доступ к API, второй прокси в будущем) безопасного отката нет. Для N=1 результат совпадает с выбранным вариантом. |
| Доверять `X-Forwarded-For` всегда (самый правый элемент без настройки) | При прямом обращении к API (локальная разработка, ошибка в сети docker) правый элемент подделывается клиентом. Явная настройка заставляет осознанно объявить, сколько прокси за нами. |
| По умолчанию `TRUSTED_PROXY_COUNT=1` | Небезопасный дефолт для разработки и любого запуска без прокси. |
| Парсить `Forwarded` (RFC 7239) | Nginx его не ставит, лишняя поверхность. |
| Задавать число через `AUTH_ORIGIN`/эвристики | Скрытая магия, нельзя проверить. |

## Допущения и что нужно сделать при выкатке

- **Деплой: добавить `TRUSTED_PROXY_COUNT=1` в `homelab/env/i-finances.env`** (и в `i-finances.env.example`; это отдельный репозиторий homelab, здесь не менялся). Пока значение не задано, действует безопасный дефолт 0: адрес клиента = адрес контейнера nginx в сети `if-net`. Сбоя нет, но все клиенты выглядят как один адрес: ключ `ip:username` вырождается в ключ по одному username, а в `sessions.ip_address` пишется адрес nginx. Лимит по username (см. `login-rate-limit.md`) при этом работает в полную силу.
- Если когда-нибудь перед nginx появится CDN или балансировщик, `$remote_addr` в nginx станет адресом CDN: нужно настроить `real_ip_header`/`set_real_ip_from` в nginx и/или увеличить `TRUSTED_PROXY_COUNT`. До этого все клиенты окажутся «одним адресом» (лимит срабатывает строже, а не слабее).
- Docker при публикации портов через userland-proxy может показывать IPv6-клиентов как адрес шлюза docker-сети. Последствие то же: общий ключ, строже, не слабее.
- Подмена IPv6 внутри подсети /64 даёт клиенту много «разных» адресов для ключа `ip:username`; это закрывает отдельный лимит по username.
- Новые контроллеры (Telegram, приглашения из IF-44) обязаны брать адрес только через `readClientIp`.
