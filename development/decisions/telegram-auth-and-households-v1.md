# Вход через Telegram и окружения (household) v1

Задача IF-44. Автор: Opus-архитектор, 2026-10-18. Статус: принято к реализации (решения владельца не оспариваются, остальное решено здесь с причинами).

Документ блокирует IF-37 (доски макета) и API IF-10. Разбивка IF-10 на подзадачи в разделе 8, миграции БД выделены отдельно в разделе 8.1.

## 1. Контекст

**Решения владельца (входные данные):**

- пользователь состоит только в **одном** окружении;
- регистрация и вход через Telegram приходят **первыми** (проверено владельцем в ShopperTodo и ServicePlanner);
- приглашение в окружение — **одноразовая ссылка**, срок по умолчанию 7 дней (разрешено пересмотреть);
- у `users` нет email, `password_hash` обязателен; есть вход по паролю и по ключу доступа (WebAuthn).

**Что в коде i-finances сейчас (проверено 2026-10-18):**

- `households`, `household_members` (PK `household_id + user_id`, роли `owner`/`member`, обычный индекс по `user_id`, то есть схема допускает несколько окружений у человека).
- `household-resolver.ts`: если у пользователя нет окружения, **создаёт `default-household` и делает его `owner`** (любого пользователя, включая второго члена семьи). При двух окружениях бросает `HouseholdSelectionRequiredError`. В файле три класса — нарушение правила «один класс — один файл».
- Все сервисы (`account`, `category`, `contact`, `operation`, `transfer`, `receipt-import`, контроллер курсов) получают окружение через `householdResolver.requireForUser(userId)` и фильтруют по `household_id`. Изоляция уже построена правильно; хардкод остался в трёх местах: автосоздание в резолвере, `seed-auth-user.ts` и **публичный `GET /api/public/categories`** (без входа, CORS `*`, отдаёт категории `DEFAULT_HOUSEHOLD_ID`).
- Сеансы: непрозрачный токен в httpOnly-cookie, в БД только SHA-256 хеш, срок `SESSION_TTL_DAYS`. Мутации проверяют `Origin`/`Referer` против `AUTH_ORIGIN`.
- Ключ доступа: вход без имени пользователя (`generateAuthenticationOptions` без `allowCredentials`), регистрация ключа требует сеанса, `userName` в WebAuthn = `users.username`.
- MCP: `ApiKeySessionResolver` по `MCP_API_KEY` выдаёт себя за `MCP_USER_ID`; окружение определяется членством этого пользователя.
- Миграции применяются **при старте контейнера** (`CMD ... migrate-db.ts && main.ts`) через `applyMigrations`, который выключает `foreign_keys` до транзакции мигратора (урок миграции 0012 с пересборкой таблицы). Шаблон теста миграции на заполненной базе есть: `apps/api/tests/transfer-migration.test.ts`.
- Курсы валют берутся только из НБРБ, и клиент поддерживает только базовую валюту BYN (`national-bank-client.ts`: `if (input.baseCurrency !== 'BYN')`).
- Локальная база: одно окружение `default-household` («Семья»), 2 пользователя, членство только у одного (`owner`). На проде (по памяти деплоя) тоже 2 пользователя; роли на проде проверить запросом только на чтение перед миграцией (раздел 8.1, DB-3).

## 2. Что проверено на практике в ShopperTodo и ServicePlanner

Код и документы прочитаны в `/Users/stark/Documents/web/shopper-todo` и `/Users/stark/Documents/web/service-planner`. Секреты и `.env` не открывались.

### 2.1. ShopperTodo: Telegram Login Widget

- Виджет `telegram-widget.js?22` с `data-onauth`, `data-request-access="write"`; фронт отправляет payload на `POST /api/auth/telegram`.
- Проверка подписи: `secret = SHA256(bot_token)`, `hash = HMAC_SHA256(secret, data_check_string)` в hex, где `data_check_string` — все поля кроме `hash`, отсортированные по ключу, `key=value` через `\n`. Сравнение `timingSafeEqual`. `auth_date` не старше **24 часов**.
- Первый вход = регистрация: upsert `users` по `telegram_id UNIQUE`, сеанс — случайный токен, в БД хеш. Пароль удалён целиком.
- Приглашение — **постоянный** `invite_token` на списке, перевыпуск инвалидирует старую ссылку; токен приглашения сохраняется в `sessionStorage` до входа и забирается после (`pending-invite.ts`).
- Rate-limit в памяти, фиксированное окно, ключ — адрес клиента из `readClientIp` (`http/client-ip.ts`, см. `client-ip.md`; 10 входов за 5 минут), только на открытых точках (вход и присоединение).

**Грабли ShopperTodo:**

1. Виджет работает только на домене, привязанном в BotFather (`/setdomain`, один домен на бота). На localhost пришлось подписывать payload вручную.
2. Подписанный payload — предъявительский документ: кто его перехватил, тот входит в течение 24 часов, учёта использованных `hash` нет.
3. Найдено при чтении кода (на практике не проявилось): сервер собирает payload из белого списка полей и делает `trim`. Если Telegram добавит поле или в имени окажется пробел по краям, подпись перестанет сходиться. Проверять подпись надо по сырому объекту.

### 2.2. ServicePlanner: бот по deep-link (решение 2026-09-30, на проде с 2026-10-01)

- Не виджет и не Mini App: **ссылка `https://t.me/<bot>?start=<код>`** (плюс `tg://resolve?domain=<bot>&start=<код>`). Причины из их дорожной карты: на телефоне открывается приложение Telegram, всё работает **в установленной PWA**, бот сразу получает право писать человеку (основа уведомлений). Проверено с телефона, в том числе из PWA.
- Поток: `POST /auth/telegram/start` создаёт заявку `TelegramLoginRequest` (код 24 байта base64url, секрет 32 байта, в БД **хеш секрета**, срок из настроек, 1–60 минут), секрет кладётся в **httpOnly-cookie браузера, начавшего вход**. Бот получает `/start <код>` через webhook и условным `UPDATE ... WHERE status=PENDING AND expires_at > now` переводит заявку в `CONFIRMED`, записывая личность из сообщения. Браузер опрашивает `complete` раз в 2 секунды (и сразу при `visibilitychange`), и первый, кто условным `UPDATE` переведёт `CONFIRMED → USED`, получает сеанс. Заявки старше суток удаляются попутно.
- Подпись данных не проверяется вовсе: личность приходит от серверов Telegram через webhook, который защищён заголовком `X-Telegram-Bot-Api-Secret-Token`.
- Webhook всегда отвечает 200 и только логирует ошибку, иначе Telegram повторяет обновление бесконечно. Режимы получения обновлений: `webhook` (прод), `polling` (разработка), `off` (тесты); в тестах `FakeTelegramBot`.
- Привязка Telegram к существующему аккаунту: тот же поток с `linkUserId`; если этот Telegram уже успел создать аккаунт-дубль без пароля и почты, он **сливается** в основной в одной транзакции (`TelegramAccountLinkService`); если у второго аккаунта есть пароль, привязка отклоняется (409).
- Dev-вход: при `DEV_LOGIN=true` API подтверждает заявку за выбранного человека вместо бота. Владелец отверг обход через пароль как костыль.

**Грабли ServicePlanner:**

1. **Дубли.** Вход через Telegram создал вторые аккаунты владельцу и Ольге, у которых уже были аккаунты по почте. Пришлось делать привязку со слиянием и сливать пары на проде руками с бэкапом. Правило владельца: «один человек — один аккаунт, не плодить дубли».
2. **Имена из Telegram** («фикус», «вика_тигра») попадали в интерфейс; понадобилось обязательное подтверждение имени.
3. Переход в бота надо делать **обычной ссылкой по нажатию**, ссылку получать заранее: открытие из `fetch().then()` Safari и PWA блокируют.
4. Боевой бот нельзя запускать локально: обновления получает один потребитель, `getUpdates` с машины разработчика отключает webhook. Нужен отдельный dev-бот или симуляция.
5. Локальная база с реальными `chat_id` и живой токен в `.env.development` отправили настоящие сообщения людям во время E2E-проверки. Тесты и стенды — только с пустым токеном и фальшивым ботом.
6. Отвязку Telegram пришлось запретить, иначе человек остаётся без входа.
7. Пользователь может заблокировать бота: `sendMessage` отвечает `403 Forbidden: bot was blocked by the user`.

## 3. Решения

### Р1. Способ входа: бот по deep-link, как в ServicePlanner

**Принято:** вход и регистрация через ссылку на бота с одноразовым кодом и подтверждением в боте **кнопкой** (усиление относительно ServicePlanner, см. Р11).

**Причины:** работает в установленной PWA и на телефоне без ввода номера на `oauth.telegram.org`; не нужен `/setdomain`; локально работает через симуляцию; бот сразу может писать человеку (уведомление владельцу о принятом приглашении, в будущем уведомления IF-38); на клиенте не нужно проверять подпись — личность приходит от Telegram по защищённому webhook. Схема уже на проде у владельца с 2026-10-01.

**Отвергнуто:**

- *Login Widget (ShopperTodo).* Всплывающее окно и ввод номера телефона при первом входе в браузере, в iOS PWA ведёт себя ненадёжно, привязка к одному домену, не работает на localhost, подписанный payload переиспользуем до истечения `auth_date`.
- *Mini App (`initData`).* Работает только внутри Telegram; i-finances — обычная PWA с ключами доступа, привязанными к домену. Может появиться в v2 как **второй** вход для тех, кто открыл бота: тогда проверка `secret = HMAC_SHA256(key="WebAppData", msg=bot_token)`, `hash = HMAC_SHA256(secret, data_check_string)`, `auth_date` не старше 5 минут, проверка по сырой строке `initData`, без белого списка полей.

### Р2. Модель данных: отдельная таблица `telegram_accounts`

**Принято:** таблица один-к-одному с `users` (PK = `user_id`, `telegram_id` UNIQUE). Схема в разделе 4.

**Причины:** PK по `user_id` и UNIQUE по `telegram_id` вместе дают «один человек — один Telegram». Данные Telegram (username, имя, `chat_id`, признак блокировки бота) обновляются при каждом входе и не трогают `users`. Привязка и отвязка — вставка и удаление строки. Таблица `users` остаётся узкой.

**Отвергнуто:** колонки `telegram_*` в `users` — смешивает профиль и внешнюю личность, а nullable-колонка с уникальным индексом ничем не проще отдельной таблицы.

`telegram_id` храним **строкой**: это идентификатор, а не число для арифметики; в JSON и логах точность не теряется.

### Р3. `password_hash` становится необязательным

**Принято:** миграция делает `users.password_hash` nullable (пересборка таблицы, миграция DB-2). Пользователь, пришедший через Telegram, пароля не имеет. `username` остаётся обязательным и уникальным; для пользователей из Telegram генерируется `tg-<telegram_id>`, по нему никто не входит (пароля нет), в интерфейсе он не показывается.

**Причины:** честная модель («пароля нет») вместо значения-заглушки. IF-41 (смена пароля со старым паролем) и вход по паролю должны явно различать «пароля нет». Пересборка таблицы с внешними ключами уже решена в проекте (`applyMigrations`, миграция 0012) и проверяется тестом по шаблону `transfer-migration.test.ts`.

**Отвергнуто:**

- *Значение-заглушка* (например, `!telegram-only`). Миграция не нужна, но `PasswordService.verify` получает не хеш, IF-41 не сможет отличить «нет пароля» от «неверный пароль», и любая новая проверка рискует пропустить заглушку.
- *Отдельная таблица `password_credentials`.* Правильно в теории, но переносит все хеши паролей, а это больше данных под риском.
- *Nullable `username`.* Расширяет пересборку, меняет контракт сеанса (`SessionUser.username`) и ключ доступа без пользы.

### Р4. Порядок «вошёл → окружение»

1. Вход через Telegram. Telegram известен → сеанс этого пользователя. Неизвестен → создаётся пользователь (`display_name` из имени и фамилии Telegram, без пароля) и строка `telegram_accounts`, затем сеанс. Если `TELEGRAM_REGISTRATION_ENABLED=false`, неизвестный Telegram получает отказ «Аккаунт не найден. Войдите паролем или ключом доступа и привяжите Telegram в разделе «Безопасность»».
2. Пользователь без членства в окружении — **состояние онбординга**: сеанс действителен, `GET /api/auth/session` отдаёт `household: null`, все эндпоинты окружения отвечают 403 с кодом `household-required`. Веб показывает экран «Добро пожаловать»: подтвердить имя (подставлено из Telegram, урок «фикуса»), затем выбрать «Создать своё окружение» или «У меня есть приглашение».
3. Пришёл по ссылке приглашения: токен сохраняется в `sessionStorage` до входа (как `pending-invite` в ShopperTodo), после входа показывается экран принятия, онбординг пропускается.
4. Окружение создаётся **только явно**, автосоздания больше нет.

Базовая валюта нового окружения в v1 — **только BYN**: курсы берутся из НБРБ, и клиент другие базовые валюты не поддерживает. Выбор валюты — после появления второго источника курсов (не в IF-10). Новое окружение создаётся без категорий; стартовый набор категорий — отдельная задача после ревизии таксономии (`development/category-taxonomy-revision-plan.md`), для v1 нужен пустой экран на доске.

### Р5. Приглашения

**Принято:** таблица `household_invitations` (раздел 4). Токен — 32 случайных байта base64url (43 символа), в БД только SHA-256 hex. Ссылка `https://<домен>/invite/<токен>` показывается **один раз** при создании («Скопировать», «Поделиться»), повторно её получить нельзя: только отозвать и создать новую.

- **Одноразовость:** принятие — одна транзакция: условный `UPDATE household_invitations SET accepted_at=?, accepted_by_user_id=? WHERE id=? AND accepted_at IS NULL AND revoked_at IS NULL AND expires_at > ?`, проверка `changes === 1`, затем вставка членства. Второе принятие получает «Ссылка уже использована».
- **Срок: 72 часа** вместо 7 дней (`HOUSEHOLD_INVITATION_TTL_HOURS`, по умолчанию 72, допустимо от 1 до 168). Причина: ссылка даёт полный доступ ко всем финансам семьи и пересылается через мессенджеры, где остаётся в истории. Родственник обычно принимает её в тот же день; 72 часа покрывают выходные; новая ссылка — одна кнопка. Компенсация риска: владелец получает сообщение бота о принятии («Анна присоединилась к окружению «Семья»») и может сразу удалить участника.
- **Лимит:** не больше 3 активных приглашений на окружение.
- Приглашение не привязано к конкретному Telegram-аккаунту: username необязателен и меняется. Отвергнуто для v1.
- Предпросмотр по токену (`GET /api/invitations/:token`) публичный и отдаёт только название окружения, имя пригласившего и статус (`active`/`expired`/`used`/`revoked`/`not-found`). Подобрать 256-битный токен нельзя, лимит частоты всё равно стоит.
- SPA после чтения токена из URL сразу заменяет адрес (`history.replaceState` на `/invite`) и хранит токен в `sessionStorage`, чтобы он не ушёл в `Referer` и историю.
- Если принимающий уже состоит в окружении: если он **единственный участник, и окружение пустое** (нет счетов, операций, переводов, чеков, контактов, категорий), это окружение удаляется в той же транзакции и человек переходит по приглашению (защита от случайно созданного окружения и дублей); иначе отказ «Вы уже состоите в окружении «X». Чтобы перейти, сначала покиньте его». Отказ, а не перенос, потому что данные одного окружения нельзя молча сливать в другое.

**Отвергнуто:** постоянная ссылка с перевыпуском (ShopperTodo) — противоречит решению владельца и опасна для финансов; хранение токена открытым текстом — утечка БД открыла бы вход в окружения; подтверждение владельцем каждого принятия — лишний шаг для семьи, его заменяет уведомление о принятии.

### Р6. Роли owner и member

| Действие | owner | member |
|---|---|---|
| Все финансовые данные (чтение и правка) | да | да |
| Название окружения | да | нет |
| Приглашения: создать, увидеть активные, отозвать | да | нет |
| Удалить участника | да, кроме себя | нет |
| Покинуть окружение | нет, если он последний owner | да |

Создатель окружения становится `owner`, принявший приглашение — `member`. Инвариант: в окружении всегда есть хотя бы один owner. Повышение до owner, передача владения и удаление окружения — v2. Существующие роли миграция не меняет (раздел 8.1, DB-3).

### Р7. Удаление участника и завершение его сеансов

`POST /api/household/members/:userId/remove` (только owner, не себя) в одной транзакции удаляет членство и **все сеансы** этого пользователя (`sessions WHERE user_id = ?`). Пользователь, ключи доступа и привязка Telegram остаются: человек может войти снова и попадёт в онбординг. Созданные им операции остаются в окружении (ссылки `created_by` на `users` без каскада), строка `users` **никогда не удаляется**: иначе история потеряет автора или упадёт на внешних ключах.

Даже без удаления сеансов доступ пропадает мгновенно, потому что окружение определяется по членству на каждый запрос. Удаление сеансов — второй рубеж и то, чего владелец ждёт по смыслу. Метод `SessionRepository.deleteByUserId` общий с IF-41 («завершить все сеансы»).

Если удалённый был `MCP_USER_ID`, MCP начнёт получать `household-required`.

### Р8. Изоляция данных и снятие хардкода

- Уникальный индекс `household_members(user_id)` (миграция DB-3): «одно окружение на человека» закрепляется в схеме, а не только в коде. `HouseholdSelectionRequiredError` после этого не нужен и удаляется.
- `HouseholdResolver.requireForUser` больше ничего не создаёт: нет членства → `HouseholdAccessRequiredError` → HTTP 403 `household-required` во всех контроллерах окружения (одна общая функция отображения ошибки, не копия в каждом контроллере).
- `household-resolver.ts` разносится по файлам: `household-resolver.ts`, `household-access-required-error.ts` (и временно `household-selection-required-error.ts` до DB-3). Можно сделать раньше остального, без смены поведения.
- `DEFAULT_HOUSEHOLD_*` остаются только в `seed-auth-user.ts` (ручной скрипт для разработки). Идентификатор `default-household` в данных **не переименовываем**: это первичный ключ, на который ссылаются 7 таблиц, переименование — риск без пользы.
- `GET /api/public/categories` **закрывается**: в вебе он не вызывается (метод `listPublic` есть, вызовов нет), потребитель — старый внешний конвейер OCR (`development/receipt-ocr-migration-context.md`). Переводится под обычный сеанс или MCP-ключ, окружение берётся из сеанса.
- Тест-обход изоляции: для каждого эндпоинта окружения пользователь окружения B получает 404 (или пустой список) на идентификаторы окружения A. Сейчас такие тесты разбросаны по сервисам; нужен один HTTP-тест на все маршруты.

### Р9. Привязка Telegram к существующим пользователям

Владелец и член семьи уже есть в БД с паролями (и ключами доступа). Порядок выкатки строится так, чтобы дубли не появились (урок ServicePlanner):

1. Выкатка с `TELEGRAM_REGISTRATION_ENABLED=false`: вход через Telegram пускает только уже привязанные аккаунты.
2. Владелец и член семьи входят как обычно и в разделе «Безопасность» нажимают «Привязать Telegram» (поток `link`, раздел 5.3).
3. Только после этого владелец включает регистрацию.

Если Telegram уже создал отдельного пользователя (например, регистрацию включили раньше), привязка **вливает дубль**, только если у него нет пароля, нет ключей доступа и его окружение пустое либо отсутствует: дубль, его сеансы и пустое окружение удаляются в транзакции, Telegram переходит основному аккаунту. Иначе 409 «Этот Telegram привязан к другому аккаунту». К аккаунту уже привязан другой Telegram → 409.

**Отвязки в v1 нет** (урок ServicePlanner). В v2 — только при наличии пароля или ключа доступа.

После привязки вход по паролю и ключу **не закрывается** (в отличие от ServicePlanner, где почта была сломана): это решение владельца, все три способа остаются.

### Р10. Восстановление доступа без пароля

| Что потеряно | Как вернуть |
|---|---|
| Устройство с ключом доступа | Вход через Telegram или паролем |
| Пароль (если был) | Вход через Telegram или ключом |
| Телефон с Telegram | Telegram-аккаунт переживает потерю телефона: войти в Telegram на новом устройстве, затем в i-finances |
| Сам Telegram-аккаунт удалён (новый `telegram_id`) и нет ни пароля, ни ключа | Скрипт на сервере `reset-user-telegram.ts` (удаляет строку `telegram_accounts` и выдаёт одноразовый пароль, как `seed-auth-user.ts`); человек входит и привязывает новый Telegram. Только по слову владельца |

Отдельный UI «сброс доступа владельцем окружения» — v2. Для семейного продукта скрипт достаточен, а UI сброса — новая поверхность для атаки.

### Р11. Защита от подмены и повторов

- **Подмена личности:** личность берётся только из обновлений, которые пришли на `POST /api/telegram/webhook` с верным `X-Telegram-Bot-Api-Secret-Token` (сравнение `timingSafeEqual`). Клиент свою личность не присылает, проверять подпись нечего.
- **Перехват кода:** код из ссылки остаётся в истории чата (`/start <код>`). Без секрета из httpOnly-cookie начавшего браузера он бесполезен; секрет хранится хешем.
- **Фишинг входа («подтверди мой код»).** Атакующий начинает вход у себя и присылает жертве ссылку на бота; жертва нажимает Start, и сеанс жертвы получает браузер атакующего. Cookie от этого **не** защищает. В ServicePlanner `/start` подтверждает сразу. **Усиление в i-finances:** на `/start <код>` бот не подтверждает, а отвечает сообщением «Вход в i-finances: Safari, iOS, 18 октября 21:04. Это вы?» с кнопками **«Войти»** и **«Это не я»**. Браузер и ОС берутся из `User-Agent` запроса `start`. Подтверждение приходит через `callback_query`, личность — из `callback_query.from`. «Это не я» переводит заявку в `rejected`. Для финансовых данных лишнее нажатие оправдано.
- **Повторы:** заявка живёт 10 минут (`TELEGRAM_LOGIN_TTL_MINUTES`, 1–60), переходы `pending → confirmed|rejected → used` только условными `UPDATE` с проверкой `changes === 1` (гонка параллельных опросов отдаёт сеанс одному). Повторная доставка того же обновления Telegram ничего не меняет: условие уже не выполняется. Cookie секрета стирается после успеха.
- **`auth_date`** в нашем потоке не участвует (его нет); срок задаёт `expires_at` заявки. Для будущего Mini App — 5 минут (Р1).
- **CSRF:** `start`, `complete`, `link/*`, все мутации окружения проходят существующую проверку `isSameOriginMutation`. Webhook из проверки исключён (Telegram не шлёт `Origin`), его защищает секрет; тело ограничено `bodyLimit` (64 КБ).
- **Rate-limit** (в памяти, фиксированное окно, по образцу `LoginRateLimiter`):

| Точка | Ключ | Лимит |
|---|---|---|
| `POST /api/auth/telegram/start`, `link/start` | IP | 10 за 5 минут |
| `POST /api/auth/telegram/complete`, `link/complete` | IP | 300 за 5 минут (опрос раз в 2 с, несколько устройств за одним NAT) |
| `GET /api/invitations/:token` | IP | 30 за 5 минут |
| `POST /api/invitations/:token/accept` | пользователь | 10 за 5 минут |
| `POST /api/household/invitations` | окружение | 10 в сутки и не больше 3 активных |
| `POST /api/telegram/webhook` | — | без лимита, только секрет |

- **IP клиента:** сейчас `createMetadata` берёт **первый** элемент `X-Forwarded-For`, а nginx в homelab ставит `$proxy_add_x_forwarded_for`, то есть первый элемент присылает сам клиент. Лимит входа по паролю (ключ `ip:username`) этим обходится. Исправлено в IF-45: адрес берётся функцией `readClientIp` из `http/client-ip.ts` (N-й элемент `X-Forwarded-For` справа при `TRUSTED_PROXY_COUNT=N`, иначе адрес TCP-соседа), а не из `X-Real-IP`; причины и отвергнутые варианты в `client-ip.md`. Новые контроллеры берут адрес только через `readClientIp`.

### Р13. Влияние на MCP и ключ доступа

- **MCP** работает как раньше: `MCP_USER_ID` должен быть участником окружения (после DB-3 это гарантирует миграция; в инструкции деплоя указать, что это id владельца). Нужна только понятная ошибка `household-required` в `apps/mcp` (задача M1). Ключи MCP на пользователя (таблица вместо env) — v2.
- **Ключ доступа:** RP ID и origin не меняются. Пользователь из Telegram добавляет ключ в «Безопасности» (регистрация требует сеанса, он есть). В опциях регистрации `userName` для пользователя без пароля = `@telegram_username` или `display_name`, а не `tg-123456`, иначе это увидят в менеджере паролей (задача A10).
- **IF-41 («Безопасность», API):** ответ сеанса получает `hasPassword`; блок смены пароля для пользователей без пароля скрыт. «Задать пароль» — v2 (нужен выбор `username`). Список сеансов показывает и сеансы, созданные через Telegram (тот же `sessions`), при желании со способом входа — в v1 не нужно.

## 5. Потоки

### 5.1. Вход и регистрация через Telegram

1. Экран входа при открытии вызывает `POST /api/auth/telegram/start` и получает `{ code, botUrl, appUrl, expiresAt }`; API ставит cookie `i_finances_tg_login` (httpOnly, `SameSite=Lax`, `Secure` в проде, `Path=/api/auth/telegram`, `Max-Age` = срок заявки).
2. Кнопка «Войти через Telegram» — обычная `<a href={botUrl}>` (урок 3 ServicePlanner). После нажатия экран переходит в «Ждём подтверждения в Telegram» и опрашивает `POST /api/auth/telegram/complete { code }` раз в 2 с и сразу при `visibilitychange`.
3. Бот получает `/start <код>` и отвечает сообщением с кнопками «Войти» и «Это не я» (Р11). «Войти» → `confirmed` с личностью из `callback_query.from`, сообщение редактируется на «Готово, вернитесь в i-finances». «Это не я» → `rejected`. `answerCallbackQuery` вызывается всегда.
4. `complete`: нет cookie или хеш не совпал → 403 «Вход начат в другом браузере»; `pending` → `{ status: 'pending' }`; `rejected`, истекло или `used` → 410; `confirmed` → условный переход в `used`, поиск `telegram_accounts` по `telegram_id`, создание пользователя (если разрешено), обновление username, имени и `chat_id`, `SessionService.createSession`, cookie сеанса, стирание cookie заявки, `{ status: 'confirmed', isNewUser, hasHousehold }`.
5. `users.is_active = false` → отказ, как у пароля.

### 5.2. Онбординг и создание окружения

`POST /api/household { name }` — только без членства; создаёт окружение (`randomUUID`, базовая валюта BYN) и членство `owner` в одной транзакции. Подтверждение имени — существующий `PUT /api/auth/display-name`.

### 5.3. Привязка Telegram

`POST /api/auth/telegram/link/start` (нужен сеанс) → заявка `purpose=link, link_user_id`; бот и опрос — как в 5.1; `link/complete` проверяет, что `link_user_id` = текущий пользователь, и выполняет правила Р9. Сеанс текущего пользователя сохраняется.

### 5.4. Приглашение

Owner: `POST /api/household/invitations` → `{ id, link, expiresAt }` (ссылка один раз); `GET /api/household/invitations` → активные без ссылки; `POST /api/household/invitations/:id/revoke`.
Гость: `/invite/<токен>` → `GET /api/invitations/:token` (предпросмотр) → вход через Telegram (или паролем) → `POST /api/invitations/:token/accept` → правила Р5 → бот пишет владельцу (без ожидания, ошибки игнорируются, 403 ставит `bot_blocked_at`).

### 5.5. Участники

`GET /api/household` → `{ id, name, role, members: [{ userId, displayName, telegramUsername, role, joinedAt }] }`; `PUT /api/household { name }` (owner); `POST /api/household/members/:userId/remove` (owner, Р7); `POST /api/household/leave` (member, либо owner при наличии другого owner) → сеанс сохраняется, человек попадает в онбординг.

`GET /api/auth/session` дополняется: `household: { id, name, role } | null`, `telegram: { username } | null`, `hasPassword: boolean`. Контракты — в `packages/contracts` (zod), по файлу на смысловую группу.

## 6. Экраны и состояния для досок макета (IF-37)

Каждая доска в вариантах M (390) и D (1280), светлая и тёмная, по правилам кита (sheet на телефоне, диалог 560 на десктопе, подтверждение удаления внутри диалога).

1. **Вход (`M-/D-SignIn`, правка существующей доски IF-39).** Главная кнопка «Войти через Telegram», ниже второстепенные «Войти по паролю» и «Войти с ключом доступа». Состояния: начальное; ссылка ещё грузится (кнопка неактивна); «Ждём подтверждения в Telegram» (кнопки «Открыть Telegram ещё раз», «Отмена»); ссылка устарела («Попробовать снова»); «Вход начат в другом браузере»; «Вы отклонили вход в Telegram»; «Аккаунт не найден, регистрация закрыта» (флаг выключен); слишком много попыток; Telegram выключен на сервере (кнопки нет).
2. **Добро пожаловать (`M-/D-Onboarding`), пустой первый вход.** Поле имени, подставленное из Telegram, и выбор «Создать своё окружение» / «У меня есть приглашение» (поле для вставки ссылки). Ошибка имени.
3. **Создание окружения.** Название (по умолчанию «Семья»), строка «Основная валюта: BYN» без выбора, создание, ошибка. Затем пустая главная: нет счетов и категорий, подсказка «Добавьте первый счёт».
4. **Приглашение, гость не вошёл (`M-/D-Invite`).** «Сергей приглашает вас в окружение «Семья»» + кнопка Telegram + второстепенные способы входа. Состояния: активно; истекло; уже использовано; отозвано; не найдено.
5. **Принятие, гость вошёл.** Подтверждение «Присоединиться»; успех с переходом на главную; «Вы уже в окружении «X»» (с данными) — отказ и объяснение; «Ваше пустое окружение «X» будет удалено» — предупреждение; ошибка сети.
6. **Участники окружения (`M-/D-Household-Members`), вход из меню профиля.** Вид owner: список (имя, `@username`, роль, дата), «Пригласить», активные приглашения со сроком и «Отозвать», «Удалить участника» с подтверждением («Сеансы участника будут завершены, его операции останутся»). Вид member: список без действий и «Покинуть окружение» с подтверждением. Пустое состояние «Пока только вы». Переименование окружения (owner).
7. **Приглашение создано.** Ссылка, «Скопировать», «Поделиться», срок («Действует до 21 октября, 21:04»), предупреждение «Ссылка даёт доступ ко всем финансам окружения. Отправьте её только тому, кого приглашаете. Показывается один раз». Достигнут лимит из 3 активных.
8. **Telegram в «Безопасности» (часть `M-/D-Security`, IF-36).** «Telegram: @username, привязан 18 октября» или «Привязать Telegram»; ожидание подтверждения; ошибки «Этот Telegram привязан к другому аккаунту» и «К аккаунту уже привязан другой Telegram»; блок пароля скрыт, если пароля нет.
9. **Вас удалили из окружения.** После завершения сеанса — обычный вход, затем онбординг с плашкой «Вы больше не участник окружения «Семья»».
10. **Тексты бота** (не доска, а таблица в `development/ui-mockup.md`): приветствие на `/start` без кода, запрос подтверждения с устройством, «Готово», «Ссылка устарела», «Вход отклонён», уведомление владельцу о принятии приглашения.

## 7. Что найдено попутно

1. Лимит входа по паролю обходится подменой `X-Forwarded-For` (Р11, задача A1).
2. `GET /api/public/categories` без входа отдаёт категории семьи всему интернету (Р8, задача A8).
3. Автосоздание в резолвере делает **owner** каждого пользователя без членства, включая второго члена семьи на проде. Миграция DB-3 вставляет недостающих как `member`.
4. **Закрыто в IF-45 для API** (middleware `http/security-headers.ts`). Остаётся nginx: `AGENTS.md` (раздел Auth) обещал заголовки `x-content-type-options`, `x-frame-options`, `referrer-policy`, `permissions-policy`; заголовки API не защищают HTML SPA, который отдаёт nginx. Для страницы приглашения нужен `Referrer-Policy: no-referrer` хотя бы в nginx для `/invite` (задача A11), остальное — отдельная задача вне IF-10.

## 8. Разбивка IF-10

### 8.4. Порядок выкатки

1. **Релиз 1 (без видимых изменений):** A0, A1, DB-1, DB-2, DB-3, A5, A8, M1. Перед деплоем — чтение прод-базы (DB-3) и бэкап. Двое существующих пользователей продолжают работать как раньше.
