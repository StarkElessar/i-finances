# Приглашения в приложение и регистрация только по приглашению v1

Автор: Opus, 2026-10-22. Статус: реализовано в API (контракты, миграция 0017, тесты); право создать окружение (раздел 13, миграция 0018) — API и онбординг веба, 2026-10-23; UI приглашений не начат (доски `Flow-AppInvite`, `D-/M-AppInvitations` в `development/ui-mockup.md`). Продолжение `telegram-auth-and-households-v1.md` (Р4, Р5, Р9, Р11).

## 1. Решение владельца и что из него следует

Слова владельца: «я хочу иметь возможность пригласить В СВОЁ окружение, условно дочку... Но так же я хочу, чтобы была возможность пригласить в целом нашу программу кого-то, чтобы человек мог создать своё окружение, стать владельцем своего окружения и чтобы он мог пригласить сам свою жену... Но чтобы право приглашать именно в приложение было лишь у меня. Может быть какая-то ссылка по токену зашифрованному?»

Итог:

- регистрация новых людей **закрыта**: `TELEGRAM_REGISTRATION_ENABLED=false` остаётся выключенным навсегда (флаг не удаляется, но его включение означает «пускать всех»);
- зарегистрироваться может только тот, кто пришёл с **живой** ссылкой-приглашением одного из двух видов (раздел 2);
- создавать приглашения в приложение может только **администратор приложения** (раздел 4), на проде это владелец, логин `stark`.

## 2. Термины

| Термин | Что это | Кто создаёт | Что получает гость |
|---|---|---|---|
| **Приглашение в окружение** | `household_invitations` (Р5, есть с релиза 3) | owner любого окружения | регистрируется (если нового аккаунта ещё нет) и вступает `member` обычным `accept`; своё окружение создать не может (раздел 13) |
| **Приглашение в приложение** | `app_invitations` (новое) | только администратор приложения | регистрируется, попадает в онбординг без окружения, создаёт своё (`POST /api/household`) и становится его owner |

Ссылка у обоих видов **одна по форме**: `<origin>/invite#<токен>`. Вид определяет сервер по хешу токена; гость и веб узнают вид из `preview` (`kind`).

## 3. Кто что может

| Действие | Гость без аккаунта | Пользователь | Owner окружения | Администратор приложения |
|---|---|---|---|---|
| Зарегистрироваться без приглашения | нет | — | — | — |
| Зарегистрироваться по приглашению в окружение | да, один новый аккаунт на ссылку | — | — | — |
| Зарегистрироваться по приглашению в приложение | да, ссылка тратится | — | — | — |
| Войти существующим аккаунтом по любой ссылке | — | да, ссылка не тратится | да | да |
| Создать приглашение в окружение | — | нет | да (3 активных, 10 в сутки) | если он owner |
| Создать, увидеть, отозвать приглашения в приложение | — | нет (маршрут для него «не существует») | нет | да (20 активных, 50 в сутки, общий счёт) |
| Создать своё окружение (раздел 13) | — | только зарегистрированный по приглашению в приложение или бывший owner; пришедший по ссылке в окружение — нет, даже выйдя | да (бывший owner, в том числе после выхода) | да |

## 4. Администратор приложения

**Принято:** серверная переменная `PLATFORM_ADMIN_USERNAMES` — логины (`users.username`) через запятую. Каждый элемент обрезается и приводится к нижнему регистру так же, как логин при входе по паролю (`normalizeUsername`); пустые элементы отбрасываются; элемент, который не может быть логином (`[\p{L}\p{N}._-]{3,64}`), останавливает запуск API (сообщение называет переменную, а не значение). Пусто или не задано — **администратора нет ни у кого**. Сравнивается сохранённый логин сеанса как есть с нормализованным списком: логины хранятся нормализованными (`seed-auth-user.ts`), а ненормализованный логин просто не совпадёт (проверка «закрывается», а не «открывается»). Решает `PlatformAdminPolicy` (`modules/auth/platform-admin-policy.ts`), одна функция на всё: контроллер, сервис и `GET /api/auth/session` (`isPlatformAdmin`).

Только по логину, **никогда** по `display_name` (его каждый задаёт себе сам: участница может назваться «stark», тест это проверяет) и не по роли в окружении. Логин нельзя сменить через API, у пользователей из Telegram он `tg-<id>`, префикс `tg-` зарезервирован.

**Почему переменная окружения, а не колонка `users.is_platform_admin`:**

- право выдаётся одному человеку, меняется раз в годы; колонка ради этого — миграция, UI или скрипт выдачи права и ещё одна строка в БД, которую надо защищать;
- переменную нельзя поднять изнутри приложения: ни ошибкой в коде, ни SQL-инъекцией, ни утёкшим бэкапом БД, ни утёкшим ключом MCP. Чтобы стать администратором, нужен доступ к серверу (`~/sites/homelab/env/i-finances.env`), а с ним и так есть всё;
- копия прод-базы на стенде не делает никого администратором, пока на стенде не задана переменная.

**Отвергнуто:** колонка в `users` (см. выше); «администратор — owner `default-household`» (неявное правило, сломается при передаче владения или удалении окружения в v2, и owner окружения ≠ владелец приложения); `MCP_USER_ID` как администратор (ключ MCP — Bearer, а управление допуском только по cookie, правило ревью A5).

## 5. «Токен зашифрованный?»

Шифровать нечего, и это надёжнее шифрования:

- токен — 32 случайных байта из CSPRNG (256 бит, 43 символа base64url), тот же генератор и формат, что у приглашений в окружение. Подобрать его нельзя: даже при миллиарде попыток в секунду это 10^60 лет, а `preview` ещё и ограничен 30 запросами за 5 минут на адрес;
- в БД лежит **только SHA-256** токена (`app_invitations.token_hash`, у заявки входа — `telegram_login_requests.invitation_token_hash`). Утечка БД или бэкапа не даёт ни одной рабочей ссылки; шифрованный токен, наоборот, расшифровывался бы ключом с того же сервера;
- токен во **фрагменте** URL (`#…`): браузер не отправляет фрагмент никогда, поэтому его нет ни в журнале nginx, ни в `Referer`, ни у превью ссылок в мессенджерах (решение ревью A6). В API токен ходит только в JSON-теле;
- ссылка показывается **один раз** при создании, повторно её не получить: только отозвать и создать новую;
- **одноразовость и срок:** приглашение в приложение тратится при регистрации, живёт 7 дней (`APP_INVITATION_TTL_HOURS`, 1–168, как у приглашений в окружение), администратор может отозвать его в любой момент.

То, что остаётся, одинаково для любого «шифрования»: тот, у кого есть ссылка, может ею воспользоваться. Защита от этого — одноразовость, короткий срок, отзыв и то, что администратор видит, кто зарегистрировался (имя и `@username` в списке).

## 6. Регистрация по приглашению

### 6.1. Поток

1. Гость открывает `/invite#<токен>`, веб делает `POST /api/invitations/preview { token }` и по `kind` показывает «Вас пригласили в i-finances» (`app`) или «X приглашает вас в окружение «Y»» (`household`).
2. `POST /api/auth/telegram/start { invitationToken }` (тело необязательно, пустое тело = `{}`, как раньше). Неверный формат токена → 400 `invalid-input` до всякой работы с БД (после лимита частоты). Токен верного формата хешируется; если хеш открывает живое приглашение любого вида (`findActiveInvitationKind`), к заявке привязывается **только хеш**; иначе заявка обычная. Ответ одинаковый в обоих случаях, `start` о токене ничего не говорит. Лимит частоты прежний (10 за 5 минут на адрес, общий с `link/start`), он проверяется до поиска.
3. Бот: «Войти» → `confirmed` (без изменений). Текст после нажатия — «Вход подтверждён» или «Аккаунт не найден», как раньше; «подтверждён» теперь и тогда, когда к заявке привязано живое приглашение. Бот никогда не говорит о приглашениях и их видах: тексты те же два, новых нет.
4. `complete`: Telegram известен → обычный вход, приглашение **не трогается** (и не тратится). Неизвестен → `TelegramAccountRepository.signIn` (единственное место создания пользователя), одна синхронная транзакция:
   1. `findActiveInvitationKind(transaction, hash)` — заново, внутри транзакции: живо ли приглашение сейчас;
   2. флаг выключен и живого приглашения нет → `not-found` → 403 `registration-closed` (тот же код и текст, что и раньше, для любой причины: нет приглашения, просрочено, отозвано, использовано, гонка);
   3. вставка `users` и `telegram_accounts`;
   4. `reserveRegistrationInvitation` — условный `UPDATE`, повторяющий все условия активности, `changes === 1`: для `app` ставит `accepted_at`, `accepted_by_user_id`; для `household` ставит `registered_user_id`, само приглашение остаётся активным;
   5. если `UPDATE` ничего не изменил (кто-то успел первым) и флаг выключен → `rollback()`: откатывается всё, включая пользователя, ответ `registration-closed`. Из двух регистраций одной ссылкой проходит ровно одна.
5. Новый пользователь без окружения → онбординг. По приглашению в приложение он создаёт своё окружение (`POST /api/household`, без изменений) и становится owner. По приглашению в окружение веб показывает принятие (`accept`, без изменений).

### 6.2. Решение: одна регистрация на приглашение в окружение

Задание: приглашение в окружение при регистрации **не потребляется**, но должно быть живо. Если сделать только это, одна ссылка owner'а (живёт 7 дней) регистрирует **сколько угодно** новых аккаунтов: каждый, у кого она оказалась, проходит, пока ссылку никто не принял. Регистрация закрыта ради того, чтобы новых людей впускали осознанно, поэтому принято: приглашение в окружение даёт **один** новый аккаунт. Это отдельная колонка `household_invitations.registered_user_id` (миграция 0017), а не потребление: `accept` работает как раньше (по-прежнему один раз, любым вошедшим), предпросмотр показывает приглашение живым. Второй новый человек с той же ссылкой получает `registration-closed`; уже зарегистрированный входит как обычно.

### 6.3. Флаг включён

Если владелец когда-нибудь включит `TELEGRAM_REGISTRATION_ENABLED=true`, регистрация пускает всех, а привязанное живое приглашение всё равно тратится (чтобы им не воспользовался ещё кто-то); если потратить не удалось, регистрация проходит по флагу.

## 7. Миграция 0017

`apps/api/drizzle/0017_app_invitations.sql`, получена `pnpm --filter @i-finances/api db:generate --name app_invitations` без правок:

- `CREATE TABLE app_invitations` (`id` PK, `token_hash` NOT NULL UNIQUE, `created_by_user_id` NOT NULL → `users`, `note` NULL (≤ 80 символов, проверяет контракт), `expires_at`, `created_at` NOT NULL, `accepted_at` NULL, `accepted_by_user_id` NULL → `users`, `revoked_at` NULL), индексы `app_invitations_token_hash_unique`, `app_invitations_created_at_idx` (суточный лимит и список). Внешние ключи на `users` без каскада: пользователи не удаляются (Р7);
- `ALTER TABLE household_invitations ADD registered_user_id text REFERENCES users(id)`;
- `ALTER TABLE telegram_login_requests ADD invitation_token_hash text`.

`ALTER TABLE ... ADD COLUMN` в SQLite допустим для nullable-колонки без значения по умолчанию, в том числе с `REFERENCES`: таблица не пересобирается, строки не трогаются, существующий DDL дополняется одной колонкой (тест сравнивает DDL до и после). Предохранитель 0015 и `applyMigrations` здесь не нужны, но и не мешают.

Проверено: контрольные суммы 0000–0016 и их снапшотов не изменились (журнал только дополнен записью 0017); `drizzle-kit check` чистый, повторный `db:generate` — «No schema changes». Тест `tests/app-invitations-migration.test.ts`: база на 0016 с данными (пользователи, окружение, участники, сеанс, Telegram, три приглашения в окружение в разных состояниях, две заявки входа) → `applyMigrations` → все строки на месте, новые колонки NULL, `foreign_key_check` пуст, `integrity_check` ok, схема изменилась только на новую таблицу и две колонки, новые ограничения работают, повторный прогон ничего не применяет. Тест `telegram-households-migration.test.ts` теперь применяет миграции до 0016 включительно (он фиксирует именно 0014–0016).

**Выкатка** (`docs/deployment.md`, раздел «Invitations into the application»): бэкап через контейнер `backup` (`schema-migrations-v1.md`, 5.2), переменная `PLATFORM_ADMIN_USERNAMES=stark`, пробный прогон на копии бэкапа из нового образа (5.3), выкатка API и веба вместе, smoke (`isPlatformAdmin` у `stark` — `true`).

**Откат — откат кода** (`git revert` слияния и обычная выкатка). Старый код совместим со схемой после 0017: новую таблицу и колонки он не читает, вставки в `telegram_login_requests` и `household_invitations` перечисляют только известные ему колонки (новые остаются NULL), его мигратор ничего не применяет. Что меняется после отката: приглашения в приложение перестают работать (их ссылки — `unknown`), зарегистрированные по ним люди остаются. Одна разница поведения: старое вливание дубля при привязке Telegram (Р9) не знает о ссылках `app_invitations` и `registered_user_id`, и для такого дубля удаление пользователя упадёт на внешнем ключе (500, транзакция откатится, данные не теряются) вместо 409. Восстановление из бэкапа — только при повреждённой базе (теряется всё после бэкапа). Обратной миграции нет (`schema-migrations-v1.md`, 7).

## 8. Контракты для UI

Все — в `packages/contracts` (`app-invitation.ts`, `household-invitation.ts`, `telegram-auth.ts`, `auth.ts`).

**`POST /api/auth/telegram/start`** — тело `{}` или `{ invitationToken: string }` (`telegramSignInStartInputSchema`, 43 символа base64url). Ответ прежний. 400 `invalid-input` для неверного формата или не-JSON.

**`POST /api/auth/telegram/complete`** — без изменений; для неизвестного Telegram без живого приглашения — 403 `registration-closed`.

**`POST /api/invitations/preview { token }`** — 200:

```ts
{ ok: true, invitation: { kind: 'household', expiresAt, householdName, inviterName } }
{ ok: true, invitation: { kind: 'app', expiresAt, inviterName } }   // без householdName, без заметки
```

Мёртвая ссылка любого вида — прежний 404 `invitation-unavailable` с `reason: 'expired' | 'used' | 'revoked' | 'unknown'`, той же формы. Оба вида всегда ищутся (по одному запросу в каждой таблице), работа одинакова для всех причин и видов (тест считает запросы). В схеме `kind` и `householdName` необязательны **только** ради совместимости с вебом, написанным до этой задачи (истории и тесты строят `InvitationPreview` без `kind`); API всегда отдаёт `kind`, уточнение схемы требует `householdName` ровно при `kind !== 'app'`. Ответ без `kind` — приглашение в окружение.

**`POST /api/invitations/accept`** — для живого приглашения в приложение: 409 `app-invitation-not-acceptable` («Это приглашение в приложение, а не в окружение: создайте своё окружение.»), ничего не меняется. Мёртвое приглашение в приложение — 404 `invitation-unavailable` с его `reason`.

**`GET /api/auth/session`** — добавлено `isPlatformAdmin: boolean` (в схеме необязательно по той же причине совместимости, API отдаёт всегда).

**Маршруты администратора** (только cookie-сеанс):

```ts
POST /api/app-invitations            { note?: string }        // ≤ 80 символов после trim, без управляющих и форматирующих
  201 { ok: true, invitation: { id, link, expiresAt } }       // link = <origin>/invite#<token>, единственный раз
GET  /api/app-invitations
  200 { ok: true, invitations: Array<{
        id, note: string | null, createdAt, expiresAt,
        status: 'active' | 'accepted',
        acceptedAt: string | null,
        acceptedBy: { displayName, telegramUsername: string | null } | null }> }
      // активные и принятые за последние 30 дней, новые сверху, до 100 строк; отозванных и просроченных нет
POST /api/app-invitations/:id/revoke
  200 { ok: true }
```

Ошибки (`appInvitationFailureSchema`, `{ ok: false, errorCode, message, fieldErrors? }`): 401 `unauthenticated` (нет сеанса, в том числе Bearer/MCP); 403 `invalid-origin`; 400 `invalid-input` (`fieldErrors.note`); 413 `payload-too-large`; 409 `invitation-limit-reached` (20 активных); 429 `rate-limited` (50 за сутки); 404 `invitation-not-found` (отзыв неизвестного или уже неактивного). **Не-администратору** любой из трёх маршрутов отвечает ровно как несуществующий маршрут: 404 `{ ok: false, error: { code: 'not_found', message } }` (одна функция `respondNotFound` для обоих), независимо от метода, тела, его размера и `Origin`: проверка администратора стоит первой, до лимита тела и проверки источника. Для UI это значит: 404 `not_found` на этих маршрутах = «права сняли» (на доске это нарисовано как 403, см. раздел 11).

**Граница маскировки (ревью Opus и Codex Astra, 2026-10-22).** Неразличим только HTTP-ответ вошедшему не-администратору (статус, тело и все заголовки, тесты сравнивают их с настоящим 404). Существование маршрутов этим не скрыто: без сеанса они отвечают 401, а несуществующий маршрут — 404 (выйти из аккаунта может любой); сеанс разрешается до ответа, поэтому сеанс с `last_seen_at` старше суток «трогается» (видно в списке сеансов), а на несуществующем маршруте — нет; код открыт в репозитории. Это принято: защита — проверка администратора, а не тайна маршрута; маскировка лишь не подсказывает обычному пользователю, что у кого-то есть больше прав.

## 9. Модель угроз

| Угроза | Защита | Тест |
|---|---|---|
| Посторонний регистрируется без приглашения | флаг выключен; без живого приглашения в транзакции — `registration-closed` | M3 |
| Подбор токена | 256 бит, лимит `preview` 30/5 мин на адрес, лимит `start` 10/5 мин | — |
| Одна ссылка в приложение — много аккаунтов (гонка) | проверка и трата внутри транзакции создания пользователя, условный `UPDATE` с `changes === 1`, иначе откат пользователя | гонка, триггер-тест, M4, M10 |
| Одна ссылка в окружение — много аккаунтов | `registered_user_id`, одна регистрация на ссылку (раздел 6.2) | M13 |
| Ссылка утекла | одноразовая, 7 дней, отзыв, администратор видит, кто зарегистрировался | отзыв, просрочка, M6 |
| Утечка БД или бэкапа | только SHA-256 токена (и в приглашении, и в заявке) | хеш в заявке, «токена нет нигде», M7 |
| Токен в журналах | фрагмент URL, тело запроса, ответы через схемы контрактов | — |
| Обычный пользователь создаёт приглашение в приложение | `PlatformAdminPolicy` в контроллере и в сервисе | M1, M12, тест изоляции |
| Подмена администратора именем | только `users.username`; имя не участвует | M2 |
| Утечка `MCP_API_KEY` (его пользователь — администратор) | маршруты на cookie-резолвере, Bearer → 401 | M9 |
| Пользователь узнаёт, что функция есть | 404 как у несуществующего маршрута до любых других проверок | M14, тест изоляции |
| Существующий аккаунт «съедает» чужое приглашение | известный Telegram не трогает приглашение | M11 |
| Приглашение в приложение принимают как приглашение в окружение | `accept` → 409, без побочных эффектов | M15 |
| Пришедший по ссылке в окружение создаёт своё и впускает людей сам | право создать окружение (раздел 13), проверка в транзакции создания | R1–R20 |
| Различимость мёртвых ссылок по работе или форме | оба поиска всегда, одна форма ответа, отличается только `reason` | M8 |
| Бот подсказывает, что приглашение есть или какого вида | те же два текста, решение по тем же правилам | M16 |
| Фишинг входа (чужая ссылка на бота) | без изменений: кнопка «Войти» и текст с доменом (Р11) | прежние |

**Закрыто решением владельца 2026-10-23 (раздел 13).** Было «известное и принятое»: человек, зарегистрированный по ссылке в окружение, **не обязан** в него вступать: сразу после регистрации он без окружения и может создать своё (`POST /api/household`), став owner (проверено тестом ревью), а затем приглашать других в своё окружение; вступивший `member` может так же выйти (`leave`) и создать своё. То есть owner любого окружения фактически впускает новых людей в приложение (по одному на ссылку, с лимитом 3 активных и 10 в сутки на окружение), и каждый впущенный может впускать дальше: цепочка растёт без администратора. Исключительное право администратора по факту — только то, что его приглашение не показывает чужое окружение; ограничить само впускание без него нельзя. Закрыть это полностью можно только правом «создать окружение» (например, только тем, кто пришёл по приглашению в приложение, и тем, кто уже owner) — это меняет онбординг и в задачу не входило.

## 13. Право создать окружение (решение владельца 2026-10-23)

### 13.1. Решение и правило

Слова владельца: создать своё личное окружение может только тот, кто получил специальную ссылку-приглашение **в приложение** (её создаёт только администратор платформы). Иначе человек, пришедший по ссылке в окружение (например, дочь), мог не вступать или выйти, создать своё окружение, стать owner и раздавать свои приглашения: каждый owner фактически впускал бы людей в приложение.

**Правило.** `POST /api/household` создаёт окружение, только если верно хотя бы одно:

1. пользователь — **администратор платформы** (`PlatformAdminPolicy`, логин из `PLATFORM_ADMIN_USERNAMES`; единственное основание не из БД);
2. пользователь **зарегистрирован по приглашению в приложение**: на него указывает `app_invitations.accepted_by_user_id` (это поле ставит только регистрация в транзакции создания пользователя, раздел 6.1; в задаче оно названо `registered_user_id`, такая колонка есть только у `household_invitations`);
3. пользователь **когда-либо был owner** какого-либо окружения: `users.first_household_owner_at IS NOT NULL` (новая колонка, 13.3). «Был owner» — это то, что записано: время ставят создание окружения, сид и миграция 0018. **Ручное понижение до `member` через SQL (как `vicotya` 2026-10-22, `release-1-runbook.md`) не считается «был owner»:** владелец этим решением снял и право. Миграция 0018 этого не знает (шаг 2 смотрит на созданные приглашения), поэтому чтение 13.4 перед выкаткой обязательно;
4. пользователь **сейчас owner** (членство с ролью `owner`): страховка для owner, у которого время не записано (прямая вставка, работа старого кода после отката, 13.5); такой всё равно получит 409, пока состоит в окружении.

Больше ничего не даёт права: ни регистрация по ссылке в окружение (`household_invitations.registered_user_id`), ни принятие такой ссылки, ни членство `member`, ни выход или удаление из окружения, ни включённый `TELEGRAM_REGISTRATION_ENABLED`. Правило — список разрешений (allow-list): человек «без следов» права не получает. Все основания только растут (ничего их не стирает), поэтому ответ для пользователя не меняется с «да» на «нет».

Одна функция на всё: `hasHouseholdCreationRight(executor, userId)` (`modules/household/has-household-creation-right.ts`, один запрос с тремя `OR`) и `HouseholdCreationPolicy.canCreateHousehold(user)` (администратор или функция) для сеанса. `HouseholdRepository.createWithOwner` вызывает функцию **внутри той же транзакции**, что вставляет окружение и членство, первым делом, до проверки членства (флаг администратора приходит из сервиса).

**Порядок ответов `POST /api/household`:** 403 `invalid-origin` → 401 `unauthenticated` → 400 `invalid-input` → **403 `household-creation-not-allowed`** → 409 `already-in-household` → 201. Право проверяется раньше членства: участнику без права говорится «нельзя», а не «сначала покиньте» (после выхода он всё равно получил бы 403). Owner (у него право есть) по-прежнему получает 409.

**Что получает каждый:**

| Кто | Право | `POST /api/household` без окружения |
|---|---|---|
| Администратор платформы (по логину) | да | 201 |
| Зарегистрирован по приглашению в приложение (в том числе вступивший потом в чужое окружение и вышедший) | да | 201 |
| Был owner по записи: owner на момент 0018 (на проде только `stark`), создатель приглашения в окружение (кроме пониженных владельцем, 13.4), основатель окружения после 0018; в том числе вышедший или удалённый | да | 201 |
| Понижен до `member` вручную через SQL (`vicotya`) | нет | 403 |
| Зарегистрирован по ссылке в окружение, не вступил | нет | 403 |
| Вступил по ссылке в окружение (новый или существующий аккаунт), вышел или удалён | нет | 403 |
| Участник (`member`) окружения | нет | 403 (не 409) |

Вступление по приглашению в окружение (`accept`) работает для всех как раньше. Маскировка маршрутов администратора не менялась (401 без сеанса, 404 вошедшему не-администратору).

### 13.2. Почему без миграции нельзя

Проверено по схеме 0017. «Сейчас owner» выводится из `household_members`, «был owner» — нет:

- у `households` нет создателя; `leave`, удаление участника и вливание пустого окружения при `accept` удаляют строку членства вместе с ролью;
- след прошлой роли есть только у тех, кто создавал приглашение в окружение (`household_invitations.created_by_user_id`: вставка проверяет роль `owner` в своей транзакции с первого дня таблицы), но это неполно: owner, ни разу не приглашавший и вышедший, следа не оставляет.

Старый резолвер делал owner'ом «Семьи» каждого, кто входил (до A5, `schema-migrations-v1.md`, 6), так что в базе, где второй owner остался, он вправе выйти (`leave` пускает, пока есть другой owner) и без записи потерял бы право. Поэтому — одна nullable-колонка. **На проде сейчас** (после 2026-10-22) owner только `stark`, второй owner `vicotya` понижен владельцем вручную, и это понижение снимает право (13.1, п. 3). Значит, на проде колонка сегодня даёт право только `stark`, у которого оно есть и как у администратора; дальше её заполняет только создание окружения людьми, у которых право и так есть. Колонка нужна для «был owner» вне прода, на случай, если `stark` уберут из `PLATFORM_ADMIN_USERNAMES`, и для будущих совладельцев (передача владения в v2); см. вопрос 7 раздела 11.

**Отвергнуто:** вывод по дате регистрации или по «нет следов приглашения в окружение» (deny-list: пропускает любого «без следов», например зарегистрированного при открытой регистрации); `households.created_by_user_id` (не покрывает унаследованных owner'ов и второго owner'а); колонка-разрешение `users.can_create_household` (это не факт, а право, которое кто-то должен выдавать; нужен скрипт или UI выдачи); триггер на `household_members` (Drizzle его не видит, а пересборка `users` или `household_members` будущей миграцией (`__new_*`, `DROP`, `RENAME`) уронила бы или сломала его молча); запись при потере роли (`leave`, удаление, `accept`) — три опасные транзакции вместо одной, при том что все пути, создающие owner'а, и так пишут время.

### 13.3. Миграция 0018

`apps/api/drizzle/0018_household_creation_right.sql`: `pnpm --filter @i-finances/api db:generate --name household_creation_right` дал `ALTER TABLE users ADD first_household_owner_at integer`; руками дописаны два шага с данными (как шаг с данными в 0016):

1. `UPDATE users SET first_household_owner_at = min(joined_at)` по членствам с ролью `owner` — все текущие owner'ы;
2. для оставшихся NULL — `min(created_at)` их приглашений в окружение (`household_invitations.created_by_user_id`): бывшие owner'ы, уже вышедшие до 0018.

`ALTER TABLE ... ADD` nullable-колонки без значения по умолчанию таблицу не пересобирает: дописывается DDL, строки не переписываются; оба `UPDATE` меняют только новую колонку. Новых объектов (индексов, триггеров) нет. Время пишут дальше: `createWithOwner` (в той же транзакции, только если NULL, раннее время не перезаписывается) и `scripts/seed-auth-user.ts` (только если пользователь действительно owner после сида).

### 13.4. Выкатка

Как 0017 (`docs/deployment.md`, раздел «Invitations into the application»): бэкап через контейнер `backup`, пробный прогон на копии из нового образа (ожидается `Database migrations applied.`, `integrity ok`, `fk violations 0`, те же количества строк), затем API и веб вместе.

**Обязательный шаг до выкатки: прочитать, кому миграция даст право** (только чтение, через контейнер `backup`, как 5.1 `schema-migrations-v1.md`: `cat <<'SQL' | docker compose exec -T backup sqlite3 -readonly -header -column /if-data/i-finances.sqlite`):

```sql
-- Кому 0018 запишет first_household_owner_at, и по какому шагу. Ожидается ровно одна строка: stark, step1.
SELECT u.username, u.display_name,
       CASE WHEN EXISTS (SELECT 1 FROM household_members o WHERE o.user_id = u.id AND o.role = 'owner')
            THEN 'step1-owner' ELSE 'step2-invitations' END AS step,
       (SELECT group_concat(m.household_id || ':' || m.role) FROM household_members m WHERE m.user_id = u.id) AS memberships,
       (SELECT count(*) FROM household_invitations i WHERE i.created_by_user_id = u.id) AS invitations_created
  FROM users u
  WHERE EXISTS (SELECT 1 FROM household_members o WHERE o.user_id = u.id AND o.role = 'owner')
     OR EXISTS (SELECT 1 FROM household_invitations i WHERE i.created_by_user_id = u.id)
  ORDER BY u.username;
```

**Ожидаемый результат: ровно одна строка, `stark`, `step1-owner`.** Шаг 2 миграции даёт право всем, кто когда-либо создавал приглашение в окружение, в том числе тем, кого владелец потом понизил до `member` вручную. Любая другая строка — **стоп**, выкатка ждёт слова владельца. Если лишняя строка — `vicotya` (понижена 2026-10-22; если она создавала приглашения, пока была owner, шаг 2 вернёт ей право), владелец решает:

- выкатывать и сразу после `healthy` снять ей время скриптом ниже (между стартом API и скриптом проходит минута; кнопки создания у неё в это время есть, но ей надо ещё выйти из «Семьи»; скрипт откатывается, если она успела стать owner, и тогда снова стоп);
- или не выкатывать, пока шаг 2 не убран из 0018 (вопрос 7 раздела 11).

Скрипт снятия (только по слову владельца, после бэкапа; меняет ровно одну строку, иначе откат):

```js
// Через контейнер if-api (база на запись), по образцу release-1-runbook.md, «Запись в боевую базу»:
```

### 13.5. Откат

Откат кода (`git revert` слияния и обычная выкатка), как у 0017. Старый код совместим со схемой после 0018: колонку не читает, вставки в `users` перечисляют только известные ему колонки (новая остаётся NULL), его мигратор ничего не применяет. После отката снова действует старое поведение (окружение создаёт любой без окружения). Одна оговорка: окружения, созданные **старым** кодом во время отката, не пишут время их owner'ам. Пока такой owner остаётся owner'ом, право у него есть (основание 4); если он потом выйдет, право пропадёт. После повторной выкатки это лечится повтором шага 1 миграции на проде (он идемпотентен: `UPDATE users SET first_household_owner_at = (SELECT min(joined_at) FROM household_members WHERE user_id = users.id AND role = 'owner') WHERE first_household_owner_at IS NULL AND EXISTS (... role = 'owner')`), только по слову владельца и после бэкапа. Обратной миграции нет.
