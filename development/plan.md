# План развития iFinances

## Назначение документа

Этот файл является актуальным источником правды о состоянии проекта и порядке
синхронизации клиентской части с backend.

Статусы:

- `[x]` — реализовано и доступно пользователю;
- `[~]` — реализовано частично или пока работает только на клиенте;
- `[ ]` — не реализовано;
- `[!]` — поведение требует исправления до фиксации серверного контракта.

## Текущая архитектура

- Клиент и сервер работают в одном SolidStart-приложении.
- Маршруты находятся в `src/routes`, страницы — в `src/views`.
- Общие бизнес-типы и чистые вычисления находятся в `src/entities`.
- Переиспользуемые контролы находятся в `src/shared/ui`.
- Серверная БД — SQLite, доступ через Drizzle ORM.
- Авторизация уже реализована через непрозрачную серверную сессию в `httpOnly`
  cookie. JWT и refresh-токены из старого плана больше не актуальны.
- Поддерживаются вход по паролю и Passkey.
- В БД хранятся пользователи, сессии, WebAuthn-данные, семья, участники, счета,
  категории и ключевые слова категорий.
- Backend CRUD счетов подключён к `HomePage` через SolidStart query/actions.
- Backend CRUD категорий подключён к странице категорий и `HomePage`.
- Контакты и операции пока не синхронизируются с backend.

## Важные исправления терминологии

В проекте должны существовать две разные валютные настройки:

1. **Базовая валюта семьи** — стабильная валюта учёта, бюджетов и исторических
   агрегатов. Для текущей семьи это BYN. Она не меняется при переключении
   профиля пользователя.
2. **Валюта отображения семейного итога** — персональная настройка пользователя.
   Например, жена видит общий баланс в USD, а муж — в BYN.

Поле операции `amountInFamilyCurrencyMinor` перед переносом в БД следует
переименовать в `amountInHouseholdBaseCurrencyMinor`. Это устранит ложное
впечатление, что историческая сумма должна пересчитываться при смене валюты
профиля.

Семейный итог по текущим балансам счетов пересчитывается в персональную валюту
по актуальному курсу. Snapshot курса операции продолжает использоваться для
исторических отчётов и никогда не заменяется текущим курсом.

## Целевая модель владения данными

Нельзя привязывать семейные категории, контакты и операции напрямую к одному
`userId`: тогда второй член семьи не увидит общие данные. Нельзя оставлять их и
полностью глобальными: это исключит поддержку нескольких семей.

Целевая модель:

- `households` — семейное пространство и его базовая валюта;
- `household_members` — связь пользователей с семьёй и роль;
- все счета, категории, контакты и операции принадлежат `householdId`;
- персональные настройки принадлежат `userId`;
- любой server query/action получает пользователя из сессии и проверяет его
  членство в семье;
- `householdId` из клиентского payload никогда не считается доказательством
  доступа.

Для первой версии роли могут быть `owner` и `member`, оба с одинаковыми
возможностями в финансовом UI. Разделение прав можно добавить позже без
изменения владения данными.

## Целевая схема БД

Все денежные суммы хранятся целыми числами в minor units. Курсы хранятся
нормализованными decimal-строками. Даты операций имеют формат `YYYY-MM-DD`,
серверные timestamps хранятся как `timestamp_ms`.

### Семья и настройки

**`households`**

- `id`, `name`;
- `baseCurrency`;
- `createdAt`, `updatedAt`.

**`householdMembers`**

- `householdId`, `userId`;
- `role`;
- `joinedAt`;
- уникальная пара `(householdId, userId)`.

**`userPreferences`**

- `userId` — PK/FK на пользователя;
- `familyTotalCurrency`;
- `updatedAt`.

**`exchangeRates`**

- `id`;
- `baseCurrency`, `quoteCurrency`;
- `rate` как decimal-строка;
- `effectiveAt`, `source`;
- уникальный индекс для валютной пары и момента курса.

На первом backend-этапе курсы можно заполнять вручную или seed-скриптом.
Интеграция с внешним провайдером не должна блокировать перенос CRUD в БД.

### Счета

**`accounts`**

- `id`, `householdId`;
- `name`, `description`, `type`, `currency`, `color`;
- `initialBalanceMinor`;
- `isColorAccentEnabled`, `isIncludedInFamilyTotal`;
- `archivedAt`;
- `createdByUserId`, `createdAt`, `updatedAt`;
- `version` для optimistic concurrency.

### Категории и ключевые слова

**`categories`**

- `id`, `householdId`;
- `name`, `color`;
- `monthlyBudgetMinor`, nullable;
- `archivedAt`;
- `createdAt`, `updatedAt`, `version`.

**`categoryKeywords`**

- `id`, `categoryId`;
- `value`, `normalizedValue`;
- `position` для стабильного порядка;
- уникальный индекс `(categoryId, normalizedValue)`.

### Контакты

**`contacts`**

- `id`, `householdId`;
- `type`: `person`, `company` или `unknown` для импортированных данных;
- `name`, `legalName`, `color`;
- `archivedAt`;
- `createdAt`, `updatedAt`, `version`.

### Операции

**`operations`**

- `id`, `householdId`, `accountId`;
- `type`: `income` или `expense`;
- `amountMinor`, `currency`;
- `amountInHouseholdBaseCurrencyMinor`;
- `happenedOn`, `sourceOrder`;
- `title`, `comment`;
- `categoryId`, `categoryNameSnapshot`;
- `contactId`, `contactNameSnapshot`;
- `exchangeFromCurrency`, `exchangeToCurrency`, `exchangeRate`;
- `deletedAt`;
- `createdByUserId`, `updatedByUserId`;
- `createdAt`, `updatedAt`, `version`.

Баланс счёта не хранится отдельным изменяемым полем. Он вычисляется как
`initialBalanceMinor + signed SUM(operations.amountMinor)` без soft-deleted
операций.

Необходимые индексы:

- `accounts(householdId, archivedAt)`;
- `categories(householdId, archivedAt)`;
- `contacts(householdId, archivedAt)`;
- `operations(accountId, happenedOn, sourceOrder)`;
- `operations(householdId, categoryId, happenedOn)`;
- `operations(householdId, contactId, happenedOn)`;
- `operations(householdId, deletedAt)`.

## Server API и слои

Используем уже принятый в проекте подход:

- SolidStart `query` для чтения;
- server actions/functions для команд;
- Zod-контракт на входе каждой команды;
- repository отвечает только за Drizzle-запросы;
- service реализует бизнес-правила и транзакции;
- entity DTO не экспортирует строки Drizzle напрямую;
- `requireUser` и проверка household membership обязательны для каждой операции.

### Запросы

- `getWorkspaceBootstrap()` — пользователь, настройки, семья, счета и актуальные
  курсы для первого экрана;
- `getAccounts()` — активные и при необходимости архивные счета;
- `getCategories({ archived })`;
- `getCategoryMonthlySummaries({ month })`;
- `getContacts({ archived, type, query })`;
- `getContactMonthlySummaries({ month })`;
- `getAccountLedger({ accountId, start, end })`.

`getAccountLedger` должен возвращать операции периода и входящий баланс до
начала периода. Тогда клиент сможет сохранить текущие сортировки и группировки,
но не будет загружать всю историю ради корректного баланса строки.

### Команды

- `createAccount`, `updateAccount`, `archiveAccount`, `restoreAccount`;
- `createCategory`, `updateCategory`, `archiveCategory`, `restoreCategory`;
- `createContact`, `updateContact`, `archiveContact`, `restoreContact`;
- `createOperation`, `updateOperation`, `softDeleteOperation`,
  `restoreOperation`;
- `updateUserPreferences`.

Команда возвращает канонический серверный DTO. После успеха клиент обновляет
локальное состояние результатом команды и инвалидирует связанные query.

### Конкурентное редактирование

Поскольку одной семьёй пользуются минимум два человека, `updatedAt` или
`version` передаётся при update-командах. Сервер обновляет запись только при
совпадении версии. При конфликте клиент получает отдельную ошибку и предлагает
перезагрузить актуальные данные, а не молча затирает изменения другого
пользователя.

Real-time синхронизация не требуется для первой версии. Достаточно:

- обновлять данные после собственной команды;
- повторно загружать активный экран при возврате фокуса;
- повторно загружать данные при переходе между маршрутами.

SSE или WebSocket следует добавлять только после появления реальной
необходимости.
